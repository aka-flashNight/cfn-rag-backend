# 04 · 检索与向量模型（services/retrieval/）

> 实施阶段 P2。目标：嵌入链路换 ONNX Runtime int8、向量存储二进制化、生产检索启用 hybrid、
> 单轮检索从「12~16 次串行嵌入+检索」降到「≤3 次嵌入 + 1 次矩阵乘」。
> 依据：`docs/v3-searching/02-联网调研-向量模型.md`（含本机实测数据）、问题清单 C1~C8、F1/F2。

---

## 1. 嵌入模型：ONNX + int8（模型不换）

### 1.1 基本事实（调研结论，直接采用）

- 现役 bge-small-zh-v1.5（24M 参数、**512 维**、MIT）已是「最小可用中文检索模型」档，**不换模型**。
- exe 357MB 主因是 torch/transformers 栈而非模型本体（92MB）。
- ONNX Runtime int8：CPU 提速 2.7~3.4x（Vespa 基准）、体积 ≈ fp32 的 1/4（→ ~25MB）；onnxruntime wheel 14MB（安装后 40~60MB），torch wheel 124MB（安装后 ~430MB）。
- 本机实测参照：fp32 单条查询 62.4ms → torch int8 21.5ms；ONNX int8 预期更低。

### 1.2 离线导出脚本 `scripts/export_onnx_int8.py`（开发机一次性执行）

```
输入：models/bge-small-zh-v1.5（HF 格式）
步骤：
 1. optimum-cli export onnx（或脚本内调 optimum API）→ fp32 ONNX
 2. onnxruntime.quantization.quant_dynamic（weight_type=QInt8）→ model_int8.onnx
 3. 拷贝 tokenizer 文件（tokenizer.json 等，给 tokenizers 库用）
 4. 校验：随机 50 句，int8 与 fp32 输出余弦相似度均值 ≥ 0.99 才允许落盘
输出：models/bge-small-zh-v1.5-onnx-int8/{model.onnx, tokenizer.json, ...}
依赖（仅 requirements-dev.txt）：optimum[onnxruntime]、torch(cpu)、transformers
```

**exe 只带 int8 产物**；torch/transformers/optimum 永不进运行时依赖。

### 1.3 运行时 `embedder.py`

```python
class OnnxEmbedder:
    """tokenizers.Tokenizer + onnxruntime.InferenceSession。
    - session 全局单例，启动时预载（预热一句空文本）。

    - encode(texts: list[str], batch_size=32) -> np.ndarray
    - 请求级缓存：同一次回合内相同 query 字符串只编码一次（修 C1 的重复嵌入）。"""
```

删除 `llama-index-embeddings-huggingface` 及 HuggingFaceEmbedding 链路。

## 2. 向量存储：二进制化（store.py）

现状：LlamaIndex JSON 向量库 50MB（4426×512 fp32 按文本存，膨胀 5.5 倍）。

新格式（落盘 `resources/tools/vector_index_v3/`）：

| 文件 | 内容 | 体积 |
|---|---|---|
| `vectors.npy` | float16[4426, 512]（fp16 足够，cosine 误差可忽略） | ~4.5MB |
| `meta.json` | `[{id, type, character, text, ...}]`（Node 元数据+原文） | ~2MB |
| `bm25.pkl` | rank_bm25 对象 + 分词缓存 | ~1MB |
| `fingerprint.json` | 语料指纹（源文件 mtime+size 集合哈希） | 小 |

```python
class VectorStore:
    matrix: np.ndarray            # [N, 512] float16
    nodes: list[Node]             # 与 matrix 行对齐
    def load(cls, dir) -> VectorStore          # 存在且指纹匹配 → 直接 mmap 加载（<1s）
    def build(cls, docs, embedder) -> VectorStore   # 全量构建，预计 ≤25s（ONNX int8）
    def save(self, dir)
```

- **指纹校验**：启动时对比 resources 源文件指纹，不一致才重建（替代旧「手动删目录」，保留前端「重置知识库」入口）。
- 旧 `vector_index/` 目录废弃（不迁移，首次启动自动重建）。
- 维度相关常量全部从模型 config 读取（512），消灭 C7 的 384 笔误。

## 3. 检索执行：单次嵌入 + 全库矩阵乘 + 池内过滤

### 3.1 原理

全库仅 4426 条。一次 `query_vec @ matrix.T`（4426×512）拿到全部相似度，耗时微秒级；之后每个池子的「类型过滤 + 阈值 + top_k」都是内存操作。**不需要 8+ 个 retriever 分别检索**——旧设计是被 LlamaIndex 的 retriever 抽象绑架了。

### 3.2 `pools.py`：池定义（配置化，修 C4）

```python
@dataclass
class Pool:
    name: str                     # npc_dialogue / world_lore / loading / npc_task
                                  # / supp_intel / other_dialogue / other_task
                                  # / game_item / game_stage
    type_filter: set[str]         # metadata.type 白名单
    character: Literal["self", "others", "any"]
    top_k: int
    dense_threshold: float        # 沿用现有魔数为初值
    rrf_k: int = 60
    max_chars: int | None         # section 截断
```

全部池子 + 阈值 + 名额策略集中在 `config.py`，一份注释写清每个数的来源（沿用旧值 or 新调）。旧的「其他 NPC 名额策略（2+3）」「彩蛋/成员阵营标注并上浮阈值」等特殊规则**保留业务行为**，但从 500 行函数体里抽成池级配置项。

### 3.3 查询计划（retriever.py）

```python
async def retrieve(ctx: TurnContext) -> RetrievalBundle:
    queries = build_queries(ctx)   # ≤3 个变体：
        # q1 = user_query；q2 = user_query + NPC名+称号+阵营；
        # q3 = user_query + npc_last_message（有才加）
    vecs = embedder.encode(queries)              # 1 次批量编码（≤3 条）
    for qi, q in enumerate(queries):
        dense_scores = matrix @ vecs[qi]         # 全库一次矩阵乘
        bm25_scores = bm25.get_scores(tokens(q)) # 全库一次
        fused = rrf(dense_scores, bm25_scores)   # k=60（调研 §4.2 共识）
        per_pool_select(fused, pools_for(qi))    # 池内过滤/阈值/topk/名额
    return merge_sections(...)                   # 行级去重、按 max_chars 截断
```

- **生产启用 hybrid**（修 C2）：dense 与 BM25 同池 RRF 融合。语料 4426 条，不属于「极小语料 RRF 反噬」区间（调研 §4.2）。
- BM25 全库打分一次 O(N)，替代旧 `filter_nodes_by_metadata` 的全量线性扫描（修 C8）；分词沿用 rank_bm25 + 现有 CJK 处理逻辑。
- 实体提示（物品/关卡子串匹配）保留但只跑 user_query 一遍，用池化后的 game_item/game_stage 结果补充（修 C6 的每轮两遍全表）。
- 「NPC 上一条发言触发第二轮」从「全池重查」改为「仅加一个 q3 变体同批融合」，语义不变，成本从 x2 降到 +1 次编码。
- `_retrieve_context` 500 行巨函数（C5）拆解为：`queries → embed → fuse → pool_select → format` 五段，每段可单测。

### 3.4 索引构建语料（loader.py，沿用现有 6 类源）

对话 XML / 任务台词 JSON / 世界观 PDF·DOCX / loading XML / 情报 TXT / 物品·关卡实体。**文档解析与切分逻辑照搬现有实现**（pypdf/python-docx/docx2txt 保留），只把 LlamaIndex `Document/StorageContext` 换成 `Node` dataclass。彩蛋/成员阵营处理规则不变。

## 4. 启动时序（配合 06）

```
startup:
  gather(
    加载 OnnxEmbedder（session 预热 ~0.5s）,
    加载 VectorStore（指纹 OK → mmap <1s；否则后台构建 ≤25s，就绪前检索降级为仅 BM25）,
    加载 GameDataRegistry,
    加载 NPC 状态库,
  )
```

首个请求不再 `ensure_embed_model_ready` 硬等全链路——embedder 就绪即可服务；索引未就绪时 Tier-1 用 BM25-only，就绪后自动升 hybrid。

## 5. 评估适配（evals/）

- `retrieve_nodes_for_eval` 改为调用新 retriever 的单池模式；三轨对比保留（dense=只用矩阵乘、bm25、hybrid_rrf）。
- golden 集与 Ragas 流程不变；评估依赖挪入 requirements-dev.txt。
- 新增基准脚本 `evals/bench_retrieval.py`：记录索引构建耗时、单次检索耗时、recall@10，用于 P2 验收与基线对比。

## 6. 验收指标（P2）

| 指标 | 要求 |
|---|---|
| 索引全量构建（4426 条） | ≤ 25s（对比基线 fp32 ~43s） |
| 单轮 Tier-1 检索（嵌入+融合+选池） | ≤ 150ms |
| 检索质量 | tiny_golden recall@10 = 1.0 不回退；full golden 与基线差 ≤ 2pp |
| 向量库体积 | ≤ 10MB（对比 58MB） |
| 运行时依赖 | 无 torch/transformers/llama-index |

## 7. 测试要求

1. embedder：int8 输出与 fp32 参考（开发机生成快照）余弦 ≥ 0.99；批量编码顺序稳定。
2. store：指纹不匹配触发重建；npy 损坏时报错并自动重建。
3. retriever：池过滤正确（self/others/any）、阈值生效、去重生效、q3 变体仅在存在上一条发言时加入。
4. RRF：构造已知排序的伪分数，验证融合序。
