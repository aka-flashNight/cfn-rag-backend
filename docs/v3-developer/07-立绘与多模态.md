## 1. 资产位置与配置

```
<游戏项目根 CrazyFlashNight>/
└── launcher/web/assets/dialogue-portraits/
    ├── manifest.json        # schema: cf7-dialogue-portraits-v2，查表唯一权威
    ├── external/p_*/e_*.png # SWF 烘焙立绘（1024×576 RGBA）
    └── internal/p_*/e_*.png # 对话框 UI 精灵烘焙（775×1000 RGBA）
```

- 配置 `CFN_GAME_PROJECT_DIR`（core/config.py），缺省自动探测：`resources` 目录的同级/上级目录中寻找含 `launcher/web/assets/dialogue-portraits/manifest.json` 的路径。
- manifest 缺失/损坏 → 记 warning，立绘功能整体降级为「无图模式」（appearance 文本仍在 prompt 中），**绝不影响聊天主功能**。
- manifest 每次进程启动现读，不缓存跨版本路径（原文 §6.7）。

## 2. 查表实现（manifest_lookup.py）

直接移植原文 §5 的 Python 参考实现（标准库即可），要点：

1. **角色归一化三注册**：原始名 / lower / 去全部空白（`[\s\ufeff]+`）后 lower；注册来源三处（entries key、entry.aliases、顶层 aliases）。
2. **情绪回退链**：请求情绪 → `普通` → `defaultExpression` → 首个表情（JSON 顺序）。
3. **路径解析**：`portrait_dir / asset.uri`，uri 相对 manifest 所在目录。
4. **主角特例**：`heroKeys`（`$PC_CHAR`/`主角模板`/`玩家`）无静态图，跳过。
5. 查不到角色 → 无图（可选用 `无头像` 条目占位，本项目选择不用，直接无图）。

> 禁止扫目录猜测 `p_*`/`e_*` hash 名；禁止硬编码情绪全集（各角色可用情绪以其 expressions keys 为准——NPC 状态库的 emotions 列表若与 manifest 不一致，以 manifest 实际命中为准，meta 解析侧无需改动，回退链自然兜底）。

## 3. 送给多模态模型的图片处理（provider.py）

- **裁剪**：一律按 `asset.bounds`（人物本体包围盒）裁剪（两类 source 通用，原文 §4）。不做游戏内取景窗口裁剪（那是 UI 展示需求，AI 识图只要人物本体）。
- **缩放**：长边 ≤ 512px（控制 token 消耗）。
- **编码**：WebP quality=80 → base64 data URL（OpenAI image_url 格式，图片 part 在文本 part 后）。
- **缓存**：key = `(npc_key, 命中情绪, 源文件 mtime)`，进程内 LRU（≤64 项）——修 F2「每请求重新 PIL 处理」。
- 情绪来源：当回合 meta 行解析出的 emo（保证图与情绪一致）；首轮 meta 未出前若需要图，用 `普通`。

## 4. 发送规则（与 02 §3.3 呼应）

| 条件 | 行为 |
|---|---|
| 模型 Profile vision=true 且 `purpose="chat"` | prompt 带图（当前情绪立绘） |
| 同上传图 400 失败一次 | 去图重试成功 → 本会话标记 vision 不可用，后续不再带图 |
| vision=false / 已标记不可用 / 无立绘资产 | 纯文本，**不报错不失败** |
| 任何子 Agent / 摘要调用 | 永不带图 |

## 5. appearance 形象描述文本（npc_state_db.json 新字段）

```jsonc
// resources/data/rag/npc_state_db.json，每 NPC 条目新增可选字段
"凯特": {
  "favorability": 0, "relationship_level": "陌生", "sex": "女",
  "emotions": [...], "faction": "...", "titles": [...],
  "appearance": "银白色短发，赤瞳，身着轻便皮甲，腰间挂着两把短刀"   // 【新增·可选】
}
```

- **有则恒入聊天 prompt**（独立于是否发图）：写在 NPC 设定块中「外貌形象：…」一行。这样即使模型不识图/无立绘，NPC 也能保持形象一致的扮演（用户要求）。
- 字段可选、缺省容忍；NPCManager 写回时保留该字段（06 §1.1 的 forward-compatible）。
- appearance 的填充是**内容工作**（后续可由小模型按立绘批量生成），不属于本次代码重构范围；代码只需支持读取与注入。

## 6. 前端展示侧

- 前端立绘展示走游戏 web 端自己的 manifest 逻辑（游戏项目自带）；本后端只需在 `meta` 事件里给出 `emotion`，前端/游戏端自行查表切图。
- 后端 `assets_api.py` 若保留「给独立前端供立绘」的接口，改为同样走 manifest 查表返回 PNG（裁剪后本体图）。
- 旧前端的「立绘生成/解压」按钮废弃 → 09 的前端适配清单中标注移除。

## 8. 测试要求（P7 验收）

1. 查表：原名/别名/大小写/带空格变体命中；缺情绪回退 `普通`；主角返回 hero；不存在角色返回 None。
2. 图片处理：bounds 裁剪正确、长边 ≤512、缓存命中时不再调 PIL。
3. 回退链：vision 模型带图 → 400 后去图成功且本会话不再带图；非 vision 模型全程无图不失败。
4. appearance：有字段进 prompt；无字段不报错。
5. manifest 缺失：启动 warning，聊天全流程不受影响。
