## 3. 端点与事件

### 3.1 `POST /api/game/dialogue-interject`

- 请求/字段：见《协议》5.1；后端负责校验：
  - `mode ∈ {daily, task}`
  - `dialogue_instance_id` 非空、长度受限、仅允许安全字符（UUID/hex）
  - `turn_id` 非空；同一 turn 幂等
  - `player_input` 非空、≤150 字；超长拒绝并记录（Host 应已限制）
  - `dialogue.kind ∈ {daily, task_pre, task_post}`，且与 `mode` 匹配（daily→daily，task→task_pre/task_post）
  - `dialogue.played/remaining/reference_continuation` 结构合法；`remaining[].index` 与 `reference_continuation[].index` 为 1..N，与模型 `n` 同口径
  - `reference_continuation` 的 edit/remove index 超出当前 `remaining` 的 N → 422（Host 记账错误，不做宽容渲染）
  - 任务模式必须有 `task_context`（completed/upcoming 至少一段；都可空则仍允许，但提示词明说没有）
- `dialogue.group_id` 是 Host 侧不透明标识（当前为 Native book 的 `requestId`，形如 `nd:N`）；后端只记录/透传，不用于 session 定位。session 定位一律用 `dialogue_instance_id`。
- `emotion` 可选；缺失按 `普通`。它只是语气提示，不参与输入校验。
- 响应：SSE，事件顺序：
  1. `status`（可选，connecting/thinking/searching/drafting/publishing/waiting；`drafting`＝拟定/修改草案，`publishing`＝确认或撤销草案的落地阶段）
  2. `mute`（任务，模型输出 mute 时，尽早）
  3. `line`（add/closing，逐句，首句尽早；拆分时带 `split:{index,count}`）
  4. `plan`（任务，完整计划；改写行同样带 `split`）
  5. `done`（成功）或 `error`（失败）
- 不把 AI 台词直接写库；以 Host finalize 的已播现场为准。
- SSE 实现注意：不要让框架的缓冲/压缩吃掉首句；逐事件 flush；客户端断开时取消 LLM/工具任务。

### 3.2 `POST /api/game/dialogue-interject/finalize`

- 请求：`{dialogue_instance_id, turn_id?, transcript:[...]}`；`transcript` 使用与请求 `played` 相同的行结构，表示该 session 截至当时的全部已播行（含历轮），后端自行做角色映射。
- 响应固定为 `{ok:true,dialogue_instance_id,session_id,appended,total}`；session 不存在且 transcript 为空时 `ok:false`、`session_id:""`。
- 语义：幂等对账；重复调用不重复写。
- 用于：每轮结束、关闭、组结束、取消后的收尾；保证 session 只包含已播内容。
- 若请求本身已带 `played`，finalize 仍建议发一次，作为“本轮实际播到哪”的权威确认。
- 允许 Host 每轮结束发一次 best-effort finalize，并在关闭/组末再发最终一次；每次 `transcript` 都是全量前缀、按 seq 幂等，关闭/组末那次为权威收尾。

### 3.3 失败

- 零有效输出：`error`（如 `no_valid_lines`），不补任何台词；Host 按《协议》D-17 回原对话。
- `error.valid_lines` 按模型输出行计、拆分前（add/closing/任务 line），`mute` 不计。
- 部分有效：已发 `line` 保留；`error`（如 `stream_failed`）；不发不完整 `plan`。
- 真取消＝客户端断开 SSE；后端在断开时取消 LLM/工具，无独立 cancel 端点；Host 随后 finalize。
- 工具失败/草案失败：记录并按现有任务链降级；不影响已发台词；必要时 `error`。

## 4. 上下文装配

### 4.1 原则

- **请求现场是权威**：`played`、`remaining`、`reference_continuation`、`player_input`、`task_context` 全部来自游戏；后端不拿 session 历史当本轮“近期对话”，避免重复/错位。
- session 只用于存储、终端回顾、记忆；不参与本轮 prompt（除非未来明确要“跨轮记忆”）。
- 复用 `context.py` 的稳定块（世界观/扮演/NPC 状态/场景/同阵营/RAG/长期记忆），但**不要**复用终端的“任务草案/说话爆发/过渡语”块；插话是独立的对话现场。

### 4.2 日常提示词块顺序（建议）

1. 世界观/时代/基本扮演规则（复用现有稳定前缀，便于缓存）。
2. 当前 NPC 扮演块（人设/说话方式/情绪白名单/关系好感度）。
3. 场景/NPC 状态/外观/装备/同阵营/记忆/RAG（按现有条件拼接；装备块与终端
   `build_static_system` 同源，经 `build_npc_equipment_block` 生成，缺失时整块省略）。
4. 本次对话现场：
   - 已播历史（当前 NPC assistant、$PC user、其他 NPC `【…】` user、玩家插话 user、AI assistant）；
   - 原对话剩余台词（仅参考，不要求逐字续写；用于保持人设/剧情/称呼）；
   - 玩家本次输入（作为 user query 的核心）。
5. 输出纪律：JSONL、add/closing、135 字、无动作描写/括号、首句尽早、结束语语义。
6. 工具说明：按日常 allowlist 注册；草案存在时加 confirm/cancel/update。

### 4.3 任务提示词块顺序（建议）

1. 世界观/扮演/NPC 状态/场景/记忆/RAG（同日常稳定前缀）。
2. 任务上下文：
   - 已完成任务：标题/目标/奖励/玩家完成了什么；
   - 将完成任务：标题/目标/奖励；
   - 任务前/后说明。
3. 本次任务对话现场：
   - 已播历史（含原作、$PC、其他 NPC、AI）；
   - 原始剩余台词（1..N，标明说话人；当前 NPC 为主）；
   - 参考续写（上一轮未播新增/改写/移除，标明原编号）；
   - 玩家输入。
4. 任务纪律：必须回到主线；只改当前 NPC；其他 NPC 一般 nochange/end；按编号；优先 end；不做无意义微调；信息不能漏。
5. 输出格式：mute/add/nochange/line/remove/end；JSONL；135 字；无动作描写。
6. 工具说明：只 query/检索 + 记忆；无任务工具、无委派。

### 4.4 上下文预算

- 任务 `remaining` 是编号基础，尽量全量；若超 token 预算，优先保留“播放点之后的连续 N 条 + 组末少量”，并在块内明确“中间省略”及编号仍按原索引；不能把编号打乱。
- 日常 `remaining` 仅参考，可按预算截取前 N 条 + 省略标记；不影响编号（日常不编号）。
- `played` 已播历史可截取最近 M 条 + 组开头少量；任务编号不受影响。
- `reference_continuation` 只保留最近一轮、必要时截断；它不参与编号。

## 6. 提示词与输出纪律

### 6.1 日常 system 要点

- 你是当前 NPC；只输出角色台词，不写旁白/动作/心理/括号。
- NPC 固定层与终端一致：外观块之后接装备块（`units.json`＋`items` 解析）；玩家名、
  场景、进度来自绑定的存档投影（`save_info`/`progress_desc`），不靠 session 历史补。
- 输出 JSONL：每行 `{"add":"…","emo":"…"}`；可选最后一行 `{"closing":"…","emo":"…"}`。
- 单条 ≤135 字；模型可自行拆多条；不要一次写超长。
- 第一句尽早输出；不要等整段。
- 结束语：若本轮话已说完，可留空；否则给一句能自然收尾的话，优先结合玩家这句话，可参考原对话剩余内容；玩家不接就结束。
- 原对话剩余内容仅作参考；不要机械续写；玩家已经切到 AI 聊天。
- 触发任务草案：不要输出过渡语；等草案就绪后只给最终确认对话+结束语；结束语表达“不接就算了”。
- 委派：只有非常必要时才调用。
- 禁止在正文中出现括号/动作描写/说话人前缀（说话人由系统字段决定）。

### 6.2 任务 system 要点

- 你是当前 NPC；玩家插话后必须回到任务原有脉络。
- 只输出 JSONL：可选 `{"mute":true}`；`add`；`{"n":k,"nochange":true}`；`{"n":k,"line":"…","emo":"…"}`；`{"n":k,"remove":true}`；最后 `{"end":k}`。
- 新增排最前；按原始编号从前往后检查；不需要改就 nochange 或 end；能接回原文必须 end；不要做无意义微调。
- 只改当前 NPC；其他 NPC 一般 nochange/end；不为其他 NPC 新增。
- 单条 ≤135 字；无动作描写/括号；第一句尽早。
- 玩家输入无法接话时：mute + 第一句无视/打断/化解，然后按正常计划接回。
- 信息不能漏；任务目标/奖励/已完成内容以提供的任务上下文为准，不要编造。

### 6.3 user 上下文格式

- 已播历史：按角色/说话人逐行；其他 NPC 用 `【NPC名：台词】`；AI 用当前 NPC；玩家用 `玩家：…`。
- 剩余：`[1] NPC名：…`、`[2] 另一NPC：…`；任务必须带编号。
- 参考续写：`上一轮未播新增：…`、`上一轮原第 3 条改写：…`、`上一轮原第 5 条移除`；明确“仅供参考，可不采用”。
- 任务上下文：已完成/将完成分块；没有则省略。
- 玩家输入：单独一块，明确“这是玩家刚刚说的话”。

### 6.4 提示词纯净

- 不写“为什么这样规定”的解释；不写未注册的工具名；不写与本轮无关的旧机制；不写“不要调用 X”除非 X 确实在本轮可用且是风险点（委派降权是例外，按用户裁定保留）。
- 规则用体系已有原词（JSONL/新增/改写/nochange/remove/end/结束语），不另造近义说法。

## 7. JSONL 解析、校验与拆分

### 7.1 解析

- 按行缓冲；去空行、去 ``` 围栏；**完全没有任何 JSON 特征**的裸台词按 `add` 兜底接收（`emo` 留空串，由 Host 回落默认表情）；带 `{}`/`[]`/`"key":` 等 JSON 特征但无法解析的行记录原文并跳过。
- 日常：只接受 `add`/`closing`；JSON 行 `emo` 缺省“普通”（裸台词兜底例外，为空串）。
- 任务：只接受 `mute`/`add`/`nochange`/`line`/`remove`/`end`；裸台词兜底按当前 NPC 的 `add`；未知字段忽略并记录。
- 每条正文（含裸台词兜底）先剥离 `（…）`/`(…)`；剥离后为空则丢弃。
- 情绪：查当前 NPC 的 `npc_state_db` 情绪白名单；非法→“普通”。任务改写其他 NPC 时，优先用原台词情绪，非法→原情绪；裸台词兜底不做情绪推导。
- 说话人：add/closing 固定当前 NPC；line 改写保留原说话人。
- 任务 `n`：1..N；越界忽略并记录；同一 n 多条 line 合并为替换多条。
- `end`：1..N 或空；越界/指向被移除→跳到下一条未移除；没有→结束。
- `nochange` 带正文/`remove` 带正文：按标记处理，正文忽略并记录。

### 7.2 拆分

- 硬上限 165；提示词 135。对每条正文/结束语：
  1. ≤165 不改。
  2. 取 ≤165 的最长前缀，优先 `。`，其次 `！？…；`，再 `，、：`，最后硬切。
  3. 剩余重复。
- 拆分后逐条 `line` 推送（`plan.edits[].lines[]` 同理）；顺序不变；同一情绪/说话人。
- 每段带 `split:{index,count}`（`index` 从 0 起，`count` 为总段数）；未拆分或缺省为自然单条。Host 只对非末段（`index < count-1`）暂锁输入，末段开始显示即恢复（《协议》3.3/D-10）。
- 拆分只对模型输出；玩家输入不拆。
- 运行时以 Native 实测校准为准；若调整，先改《协议》5.6。

### 7.3 首句与失败

- 第一条有效 line 立刻推；不等 done/plan。
- 零有效（仅剩带 JSON 特征的坏行；裸台词已由解析器兜底）：可做一次修复性重试（把原输出/错误位置给模型，要求只重发 JSONL）；仍零→error。
- 部分有效：已推 line 保留；error；不发不完整 plan。
- 取消：客户端断开时取消 LLM/工具；不写 AI 消息；finalize 以 Host 已播为准。

## 8. 任务 plan 归一化

后端负责把 JSONL 归一化成 Host 可直接应用的 plan：

```json
{
  "mute": false,
  "end": 7,
  "edits": [
    {"n":3,"kind":"nochange"},
    {"n":4,"kind":"edit","lines":[{"text":"…","emotion":"普通",
                                  "split":{"index":0,"count":2}}]},
    {"n":5,"kind":"remove"}
  ]
}
```

- `split`：一条改写正文被 165 拆分时逐段标记；未拆分的行省略。Host 用非末段暂锁输入（《协议》3.3/D-10）。
- `end: null`＝不接回原文（整组替换）。
- `n` 为 1..N，与请求 `remaining[].index` 同口径；Host 负责映射回绝对索引。
- 后端不做内容层面的“漏信息”校验；只做结构/编号/说话人/情绪/字数。
- 计划不完整（流中断）不发 plan；Host 回原对话。
- 后端日志记录：原始 JSONL 行、applied/rejected 原因、拆分结果、情绪回落、最终 plan；供走查复盘。

## 9. Session 与记忆

### 9.1 创建/复用

- `dialogue_instance_id` 由游戏生成；后端按它建/取 session。建议在 `sessions` 表新增/复用 `session_id`（或加映射列）；优先不破坏现有终端会话表结构。
- 首次插入：创建 session（title/npc_name/slot_key/来源），把请求 `played` 的前文写入。
- 后续：同一 `dialogue_instance_id` 复用；不新建。
- 同一个 turn_id 重发：不重复写玩家消息/不重复建 session。
- `group_id` 只作不透明记录；不得用它定位/合并 session。`emotion` 缺失按 `普通`，不因缺失拒绝请求。

### 9.2 角色映射

| 游戏行 | chat_history.role | content |
|---|---|---|
| 当前 NPC 原作/改写已播 | assistant | 正文 |
| `$PC` | user | 正文 |
| 其他 NPC | user | `【NPC名：正文】` |
| 玩家插入 | user | 正文 |
| AI add/closing | assistant | 正文 |

- 首次插入前已播原作要补进 session；之后每轮只追加真正已播内容。
- finalize 对账：以 Host 的 transcript 为准；重复调用幂等；未播内容不写。
- 终端列表：`/api/game/sessions` 按绑定槽位列出；title 建议见《协议》6.3。
- 终端继续：走 `/api/game/ask` 终端逻辑；不要求插入编排与终端耦合。

### 9.3 长期记忆

- 日常/任务都保留 `update_long_term_memory`；同轮完成，不额外起总结调用。
- 自动摘要若启用，以 session 已播历史为源；原作/其他 NPC 的行按角色映射参与。
- 插话本身不写 `dialogue_overrides.json` / `task_text_overrides.json`；任务草案发布是独立既有链路。
- 委派写入的覆盖层属于另一条功能；日常保留但降权，任务禁用。

## 10. 日常任务草案

- 复用现有草案/确认/发布：`route_task_draft` → 任务子 Agent → `confirm_agent_task`；不重写任务链。
- 触发草案时，插话编排在 prepare 完成（intermediate）时并发生成一条过渡话，作为 `line(interim=true)` 立即推送；草案就绪后再取最终确认对话，作为普通 `add`/`closing` 输出。若草案终态先到则取消过渡话生成，避免它在结果之后才出现。
- 玩家回复后同一 session 继续；模型可用 confirm/cancel/update。
- 草案在玩家关闭后保留；不做取消。
- 发布后的覆盖层/版本/热重载沿用既有路径；插话编排不额外写。
- 若草案生成失败：按《协议》D-17 回原对话；不输出“抱歉”等额外台词（除非现有任务链明确要求）。

## 11. 委派与并发

- 日常保留 `delegate_dialogue_rewrite`；提示词“只有非常必要时才调用”。
- handler 必须后台执行并立即返回；不得在插话请求路径里 await 子 Agent 完成。
- 若委派 worker 与插话共用 LLM 端点导致首句明显延迟：优先在插入模式停用委派（改注册闸），并记录证据；不要为了保留工具牺牲前台体验。
- 任务模式不注册委派、不注册任务工具。

## 12. 失败与降级

| 场景 | 后端行为 |
|---|---|
| 无有效 JSONL | 一次修复重试；仍无→`error(no_valid_lines)`；不补台词 |
| 部分有效后断流 | 已发 line 保留；`error(stream_failed)`；不发 plan |
| 工具失败 | 记录；能继续则继续；必要时 error |
| 草案失败 | 记录；按 D-17 回原对话；不输出额外台词 |
| 情绪非法 | 回落“普通”/原情绪 |
| 括号内容 | 剥离；为空丢弃 |
| 超 165 | 拆分 |
| 任务 n/end 非法 | 忽略/跳转；宽容继续 |
| 客户端断开 | 取消 LLM/工具；不写 AI 消息；依赖 finalize 收尾 |
| 老 exe/404 | Host 侧处理；后端不感知 |

后端不生成任何“通讯中断/信号不好”的兜底台词；失败就是没有 AI 输出，由 Host 回原对话。

### 21.4 有效池

- 赠送池：`game_data.tasks.list_core_reward_item_names()` 全量；不额外补入核心池里不存在的名字。核心池若出现 `金币/经验值/K点/技能点/强化石`，按 `_SINGLETON_PRICES` 固定单价计价。过滤无价格、战场补给、任务关键/绑定、修改器专属。
- 索取池：`item_sources` 索引中有任一来源的物品名 ∪ `{"金币"}` ∪ `request.player_item_names`；过滤同上，另剔除经验值/K点/技能点。Host 生成 `player_item_names` 时排除穿戴中的装备，装备只取背包实例。
- 装备索取：后端只按名字进池；解析到装备后数量固定 1。穿戴判断、背包多件取最低强化度、同强化度取背包第一件都由 Host/AS2 处理，后端不查实例；`item_level` 只在 accept 回传时用于拼提示。
- 关键词池内检索：复用 `ItemRegistry.search` 的匹配逻辑，但结果再按池过滤；最多 10 条。
- 抽选：从池中随机 10–20 条；索取池把金币固定放第一位，其余再抽。
- 分类计数：武器/防具/消耗品/材料/其他/金币；用 `item.type`/`item.use` + `compute_reward_tags` 归一，别另造一套分类。计数给**本轮候选之外剩余池**的构成（有效池 − 已给候选），另附有效池总数，供子 Agent 判断是否值得再查。
- 池只读；不写盘、不改任务数据。

### 21.5 解析与物品选择子 Agent

```text
resolve(name, keyword, instruction, pool, direction):
  if name and name in pool: return name
  candidates = pool_search(keyword) if keyword else []
  if not candidates: candidates = sample(pool, 10..20, gold_first=(direction=="take"))
  if not candidates: return None
  context = candidates_with_item_lines + remaining_pool_category_counts + pool_total + instruction
  first = picker.call(context)          # pick / none / search:<kw>
  if first.pick: return validate(first.name)
  if first.none: return None
  second_candidates = pool_search(first.keyword)   # only once
  if not second_candidates: return None
  second = picker.call(second_candidates + counts + instruction)  # pick/none only
  return validate(second.name)
```

- 子 Agent 输出严格 JSON：`{"action":"pick","name":"…"}` / `{"action":"none"}` / `{"action":"search","keyword":"…"}`。
- 第二轮只接受 pick/none；返回名不在池 → 失败，不把名字交给 Host。
- 单轮超时 30s，总上限 60s；失败只影响本次工具，不拖垮整轮。
- 日志：原始 name/keyword/instruction、池大小、候选数、是否再查、最终物品/失败原因。参数按原文记录，便于走查。

### 21.6 赠送价值与数量

```text
stage = blocks.progress_stage or 1          # context.py 由游戏快照 derive_progress_stage 得出
affinity = blocks.npc_state.favorability or 0
_, cap = _compute_reward_value_range(
    stage=stage, task_type="传话",
    submit_value=0, contain_value=0, affinity=affinity,
    bargain_rate=1.0,
)
price = item_price(name)   # registry / singleton map
if price <= 0: fail("无法估价")
qty = requested
if qty * price > cap:
    qty = cap // price
    if name in ("金币", "经验值"): qty = (qty // 500) * 500
if qty < 1:
    fail("你选择了赠送XXX，因价值过高，赠送失败。")
```

- `progress_stage` 与好感度都取本组已有的 `DialogueBlocks`：阶段用 `blocks.progress_stage`（`context.py` 从游戏快照的 progress/player 推导，取不到按 1），好感度用 `blocks.npc_state.favorability`（与现有 `npc_affinity` 用法同源，取不到按 0）；不要另建快照。
- `_compute_reward_value_range` 返回 `(final_min, final_max)` 二元组，赠送只看 `final_max`；`bargain_rate` 固定 1.0，不继承任务讨价还价。

- 失败结果只给聊天模型；模型必须据此拒绝，不得声称已送。
- 成功时实际 qty 可能小于请求；工具结果写明“已成功赠送 {qty} 个（原请求 {requested}，因价值上限调整）”，并附 `format_item_prompt_line` + `format_item_sources` 的物品信息块。
- 工具结果后的最终 LLM 轮 `tools=None`，system 使用不含物品工具说明的变体；不要一边说“本轮没有工具”一边还留着工具描述。
- 同一轮多个物品调用只处理第一个，其余回“已忽略（一轮只处理一个物品动作）”并记录。
- 无硬频次限制；提示词要求按关系/场景判断。

### 21.7 赠送 action 与回执

1. 工具运行时完成解析/价值裁剪，生成 `action_id`，注册 `asyncio.Future`。
2. yield `StreamAction`（`action` SSE）；`_stream_with_blocks` 暂停等待 Host 回执。
3. Host 执行 AS2 `npcItemGrant`，POST `action-result`。
4. 后端 `actions.resolve(action_id, result)`：成功 → 写账本/本组明细 → 工具结果成功；失败/超时 → 工具结果失败。
5. 回执成功时带 `actual_quantity`/`overflow_money`；工具结果按实际数量说“已成功赠送”，并附物品信息块；情报溢出折金币也要说明，不得只报请求数量。
6. 回执等待 15s；超时按失败，但记日志“可能已发放”。Host 用同 action_id 重试；后端按 `dialogue_actions(action_id)` 幂等。
7. `action-result` 端点只接受 loopback；未知/已处理 action_id 返回 `{ok:true, applied:false}`，不抛 500。

账本写入放在回执成功之后；不要在发 action 前预记成功。迟到回执（future 已超时）若物品实际已发放，仍接受同一 action_id 的结果、补写账本并记日志，但不补发本轮台词。发放成功后最终 LLM 失败不回滚物品/账本，也禁止重放 action。

### 21.8 索取 claim 状态机

```text
none --request_item 成功--> pending(claim_id,item,qty,turn_no)
pending --item_take_accept--> committed -> none
pending --item_take_decline--> declined -> none
pending --cancel_item_request--> cancelled -> none
pending --组结束/finalize/10min--> expired -> none
pending --玩家普通说话--> pending（模型可本轮取消）
```

- claim 存在进程内、按 `dialogue_instance_id` 键；一次只一个；10 分钟超时自动失效。组内轮次计数也按同一键登记，`turn_id` 幂等。
- `request_item` 成功后：写 claim，发 `item_claim(pending)`，工具结果先给 `你现在要索取物品：{qty}个{name}，该物品确认有效，可以索取。现在，请用符合你身份且符合上下文的语句，向玩家索要物品或询问玩家是否要把该物品给你。`，再附物品信息块；**最终 LLM 轮 tools=None**，不再注册赠送/索取；system 去掉物品工具说明，只保留索取指令、物品信息块与 pending claim 块。不要用“不要调用 X”这类否定句来替代机制。
- claim pending 时后续轮的 tools：`route_search`、`update_long_term_memory`、`cancel_item_request`；不注册赠送/索取，也不注册任务草案/确认/取消（先处理索取）。
- `item_take_accept`：校验 claim_id/item/qty 一致（装备 qty=1）；Host 已真实扣除；写账本；清 claim；发 `item_claim(closed)`；最终 LLM 见“玩家把 X 个 XXX 交给了你”，并保留 2–3 轮最近成功块。该轮结果块要附 claim 物品信息块（按 claim 保存的精确物品名取 `format_item_prompt_line` + `format_item_sources`；元数据缺失时至少给名称与数量），避免最终台词乱编物品属性。装备带 `item_level` 且 >1 时，文本改为“玩家把 1 个 XXX（强化度Z，{成本描述}）交给了你”，物品信息块再加一行 `强化度：Z（{成本描述}）`；成本描述按 Z<5／5≤Z≤8／Z≥9 三档；Z≤1 不加强化度。
- 装备成本描述固定文案：`经过了一定幅度的强化`（Z<5）、`经过了较高成本的强化`（5≤Z≤8）、`经过了极高成本的强化`（Z≥9）。
- `item_take_decline`：清 claim；发 closed；不写账本；最终 LLM 见“玩家拒绝赠送”。
- 玩家普通说话：claim 保留；prompt 带 pending 块；模型可调 `cancel_item_request`，调用后清 claim 并发 closed；不调用则保持。
- claim 超时/组结束：清 claim；发 closed（若流还在）。
- 单轮 `done` 不清 claim；只有 `closed`、`error`、玩家动作、组结束/超时清。
- 本轮在最终台词前以 `error` 收尾（最终轮零有效且修复失败、上游异常等）：若已发 `pending`，在 `error` 前补发 `item_claim(closed)` 并清 claim（尽力而为，发不出也要清）；下一轮不再有 pending。Host 收到 `error`/断线同样清选项。
- 玩家口头答应不算交付；只有 `item_take_accept` 才算。
- Host 已扣款但 accept 请求未达/失败：Host 保留 claim 与同 action_id 重试同一请求，不得再次扣款；后端按 `dialogue_actions` 幂等，迟到请求补写账本并清理 claim。

### 21.9 账本、组内明细与提示词块

新表：

```sql
CREATE TABLE IF NOT EXISTS npc_item_ledger (
  scope_key TEXT NOT NULL,
  npc TEXT NOT NULL,
  direction TEXT NOT NULL,          -- give: NPC→player; receive: player→NPC
  item_name TEXT NOT NULL,
  quantity INTEGER NOT NULL,
  updated_at REAL NOT NULL,
  PRIMARY KEY (scope_key, npc, direction, item_name)
);
CREATE TABLE IF NOT EXISTS dialogue_actions (
  action_id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  kind TEXT NOT NULL,               -- item_grant / item_take_accept / item_take_decline / task_accept / task_decline
  result_json TEXT NOT NULL,
  created_at REAL NOT NULL
);
```

- 作用域用 `scope_key(slot_key)`；NPC 名为当前 NPC；方向按赠送/索取。
- 写入用 upsert `quantity = quantity + excluded.quantity`；只记成功，不记失败/拒绝。
- 跨组块（进入 daily/task 插话与 embedded 终端；standalone 不注入）：

```text
【物品往来记忆（跨对话）】
你曾经送给玩家以下物品：3个XXX，1个YYY
玩家曾送给你以下物品：5个ZZZ
```

无则两行都写“无”。

- 本组块（只在 daily 插话、同一组内；组结束清空）：

```text
【本组已赠送】
第1轮：3个XXX
第3轮：1个YYY
```

- 轮次＝本组内第 N 次插话请求（turn_id），从 1 开始；同一轮多次赠送合并写在同一轮。
- 最近成功块（2–3 轮，不进账本）：`玩家刚刚给了你 X 个 XXX`（索取成功）；装备再带强化度与成本描述，如 `玩家刚刚给了你 1 个 K5项链（强化度6，经过了较高成本的强化）`；赠送成功由本组明细覆盖。
- 跨组账本仍只按物品名合并数量，不记强化度；强化度只进本轮结果块与最近成功块。
- 最近失败/拒绝（2–3 轮，不进账本）：赠送价值过高、索取找不到物品、玩家拒绝赠送。
- 放在 user 现场块（长期记忆之后），不放 system 稳定块，避免每次物品事件打断前缀缓存。

### 21.10 提示词

- **daily 工具说明**：赠送看关系/财力/讨好答谢等场景；索取看玩家主动送、声称已送、NPC 想要但不想付报酬、小东西；口头答应不算交付；调用轮不输出台词。
- **tool guide 按轮生成**：`build_daily_system_prompt` 的 tool guide 必须与本轮 `tools()` 完全一致。无 claim 的普通轮只注册赠送/索取，不注册取消；pending claim 的后续玩家输入轮只注册 `cancel_item_request`，去掉赠送/索取与任务工具；有 pending draft 时去掉物品工具；工具结果后的最终 LLM 轮使用无工具 system 变体（去掉 tool guide，保留角色/输出纪律）。不要复用带全套工具说明的稳定块还挂 `tools=None`。
- **task 提示词**：不能赠送/索取/接收；玩家提出时按情景推辞（任务紧急用任务紧急；不重要就说忙完再说）。任务本身的提交/奖励按既有任务机制，不在对话里直接交接。
- **embedded 终端**：不能接收赠送，也不能赠送玩家物品；要送就让玩家当面来；声称已送但账本没有记录＝不是真的。任务奖励、商店买卖等既有机制不受此限，只限制玩家主动赠送。
- **standalone**：不注入任何物品块，工具/行为完全不变。
- 任务模式/终端都不出现赠送/索取工具名，避免模型以为可以调用。

### 21.11 任务选项直连

- `action.kind=task_accept/task_decline`：在进入 LLM 前调用现有 `_run_confirm` / `_run_cancel`；把结果块 + 玩家原话拼进 messages；`tools=None`，跳过路由轮。
- `action_id` 同样落 `dialogue_actions` 幂等：重复/重试只返回首次结果，不重复发布或取消。首次执行结果未知（进程中断、超时）时不得自动重放发布，按既有任务发布恢复合同核对后处理。
- 失败（无草案/发布失败）同样返回结果块，模型正常回应；不要让模型再调一次路由工具。
- 只对插话请求生效；终端 `/api/game/ask` 不改。
- 确认文案生成（`generate_confirm_args`）仍在；本改造省的是路由轮，不是确认文案轮。
