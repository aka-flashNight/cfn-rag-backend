# 01 · 总体架构与核心决策

> 本文是全部重构工作的架构依据。所有模块设计以此为准；后续各章是对应模块的细化。

---

## 1. 架构全景

```
玩家消息 (HTTP /api/ask, SSE)
   │
   ▼
TurnOrchestrator（每回合一个实例，纯 asyncio）
   │
   ├─ 1. 上下文装配（并行，目标 ≤300ms）
   │     ├─ NPC 状态（内存单例）
   │     ├─ 会话记忆（SQLite：近 N 条 + 滚动摘要）
   │     ├─ Tier-1 检索（1~3 次嵌入 + 矩阵乘 + BM25 RRF，≤150ms）
   │     └─ 立绘（manifest 查表 + 缓存；仅视觉模型）
   │
   ├─ 2. 聊天主 Agent（流式 LLM 调用 #1）
   │     首行 = meta JSON：情绪（emo）/好感（fav）
   │     其后 = NPC 对话正文（实时流给前端）**或**一个路由工具调用，两者只取其一
   │     ├─ 解析 meta → 立即发 meta 事件（前端先切立绘）
   │     ├─ route_task_draft / route_task_update / route_search
   │     │      → 立即启动后台子 Agent（asyncio.Task，fire-and-steer），本轮不说话
   │     ├─ route_task_confirm / route_task_cancel
   │     │      → 后端同步执行（快，<300ms），办完再让 NPC 开口收场
   │     └─ 无路由调用 → 纯聊天，正文流完即回合结束
   │
   ├─ 3. 等待/汇合（仅当有后台子 Agent）
   │     ├─ 子 Agent 已完成 → 汇合调用 #2：携带结果，NPC 详细说明
   │     ├─ 未完成但已见中间结果 → 过渡语（只说一次、只点方向、不报数字）
   │     └─ 未完成无中间结果 → 等待（SSE 保活），拿到最终结果再汇合
   │
   └─ 4. 后处理：写记忆、更新好感、草案触碰计数、usage 落库、done 事件

后台子 Agent（与 2/3 并行运行）
   ├─ TaskRunner：LLM 工具循环（function calling）
   │     prepare_task_context → draft_agent_task / update_task_draft
   │     任务选型、校验反馈聚合、自动修复与兜底全在这里，保证拟定能完成
   └─ SearchRunner：LLM 工具循环
         search_knowledge / search_items / search_stages → 结论摘要
```

关键形态：**玩家视角 NPC 始终是「一个人」**——先说话，再「想/查/写委托」（前端显示 tool_status/ui_hint），再开口给结果。前台并行只是为了消除空窗，不向玩家暴露多 Agent 存在。

⚠ 路由轮按契约不输出台词，所以任务/确认/取消这几条路径上玩家看到的**第一句**
来自后台办完之后的第二次（或第三次）调用，中间那段静默由 `agent_status` /
`tool_status` 的等待占位承担；`prepare` 一回来就会推中间结果，过渡语随即接上，
静默期通常只有一次工具调用的时长。

## 2. D1：为什么废弃 LangGraph

问题清单证据：流式路径完全绕过编译图手写编排（B1）、四重防护全失效（B4）、死代码成堆（B6）、图框架还带入 langchain 依赖链（包体）。

新架构的控制流是「**一次流式调用 + 后台 asyncio 任务 + 检查点汇合**」，这是事件驱动模型，LangGraph 的静态图/超步模型表达它反而别扭（业界对此形态的答案是 fire-and-steer 后台子 Agent，见 `02-联网调研-Agent编排.md` §2）。HITL 靠「HTTP 轮次天然暂停 + SQLite 草案持久化」即可（现状已经如此，checkpointer 本来就没承担真正的中断恢复）。

**决策**：删除 `langgraph`、`langgraph-checkpoint-sqlite`、`langchain-openai`、`langchain-core`、`langchain-community` 依赖；删除 `services/agents/`、`services/agent_graph/`；自研 `services/orchestrator/`（预计 <800 行，单一真实路径）。

## 3. D2/D4：meta 行协议 + 路由工具（聊天主 Agent 的产出格式）

聊天主 Agent 的产出分两支：**第一行的紧凑 JSON**（只有 `emo` / `fav` 两个字段）
表达情绪与好感；**委派意图**改由 `services/tools/route/` 下的五个路由声明工具表达。
它不持有任何业务工具（`prepare_task_context` 等一律归后台子 Agent）。

- 一次调用同时产出情绪、好感变化、路由声明、对话正文——消灭 supervisor 路由 LLM（旧设计中它本身是一次完整 LLM 调用）。
- 路由工具是**声明**不是操作：编排层在流结束后读 `tool_calls` 直接分派，工具本体零副作用，所以不需要工具执行链、也不需要 `tool_choice` 强制。
- 路由判据写在工具的 `description` 里——工具表本身就是聊天主 Agent 的路由提示词，不再在 system 里重复一份（重复只会白占 token 并可能自相矛盾）。
- 不再需要旧的正文字符串截断 hack（A4 整体删除）。

**为什么委派从 meta 行搬进工具（v3 再次重构）**：`act` 塞在 meta JSON 里时，路由判据
只能写在 system 提示词中，与扮演约束、任务选型规则挤在同一块，弱模型经常在该路由时
不路由、或路由了还硬凑一句台词。改成工具后：判据随工具下发、天然结构化、可被
`agent_enabled` 开关整体摘掉（关闭时连工具表都不给，模型无从越权），聊天 system
也随之瘦掉一千多字的任务选型规则。代价是路由轮必须静默（见 §1 的静默期说明），
以及 confirm/cancel 需要一次额外的收场调用——LLM 预算仍是每回合 ≤3 次。

协议细节、解析器、容错见 `02-LLM接入层.md` §4；路由分派见 `03` §2。

## 4. D3：并行模型（fire-and-steer）

- 后台子 Agent = `asyncio.Task` + 结果 `asyncio.Queue`（progress/intermediate/final 三类消息）。不引入 Agent Protocol / 远程 deployment（那是多进程场景的方案，本地单用户过度设计）。
- steer 能力：本期内保留 `cancel()`（玩家连发新消息时取消旧后台任务）；`update`（补充指令）不实现，结构预留。
- 每会话同时最多 1 个活跃 TaskRunner + 1 个活跃 SearchRunner；同会话新回合到来时，未完成的旧子 Agent 一律取消（其副作用仅限内存与草案表，可安全丢弃；confirm/cancel 类已完成的写入不可回滚也不需要回滚）。
- 汇合规则（「中间结果只说一次话」「中间结果不报具体数字」等）是**硬性产品规则**，实现在 orchestrator，细则见 `03` §4。

## 5. SSE 事件契约（v3）

单条 SSE 连接，事件带类型。新契约（前端适配见 `09`）：

| event | data | 时机 |
|---|---|---|
| `meta` | `{emotion, favorability_change, favorability, relationship_level}` | 解析到 meta 行后立即发（正文之前） |
| `content` | `{delta}` | NPC 对话正文增量（纯台词，绝不含系统文本） |
| `tool_status` | `{tool, status, ui_hint}` | 后端工具执行进度（发布/取消等），`status ∈ running/success/failed` |
| `agent_status` | `{agent: "task"\|"search", phase, ui_hint}` | 后台子 Agent 阶段变化（拟定中/校验修复中/查询中…） |
| `system_notice` | `{text}` | 系统消息（替代旧 `{花括号}` 文本约定），如「任务草案已拟定，等待确认」 |
| `done` | `{session_id, usage{prompt_tokens, completion_tokens, cached_tokens?}}` | 回合结束 |
| `error` | `{code, message, retryable}` | 不可恢复错误 |

旧事件映射：`mood_update` → `meta`；`content` 保留但语义净化（只含台词）；`{...}` 花括号系统消息 → `system_notice`；`agent_status` 事件保留并真正展示；`done` 增加 usage。

## 6. Prompt 分层（保留并简化）

保留现有的「静态 system（L1 世界观 + 扮演约束）+ 共享 user core（RAG 块/会话状态/历史）+ 尾部指令」分层与前缀缓存对齐设计（实测 85~95%+ 命中，是有效资产），改动：

1. supervisor/决策层 prompt 全部删除；聊天尾部指令改为「meta 行协议 + 输出格式规则（【】动作、第三人称、禁半角括号等，沿用现状）」。
2. 后台子 Agent 使用**独立的小 prompt**（不含扮演约束/立绘/大部分世界观，只含任务规则或检索规则 + Skills 索引）——输入与聊天 prompt 差异很大，本就不该共享（用户决策）。Skills 渐进披露机制（list/read/read_file 三级）保留，仅子 Agent 持有。
3. 新增 `appearance` 形象描述块：npc_state_db.json 有该字段时恒常拼入聊天 prompt（无论是否发图），见 `07`。
   ⚠ 现网 `npc_state_db.json` 的 85 个 NPC 无一填 `appearance`，故该块实际恒不注入——立绘的文字说明另有兜底，见下条。
4. 情绪回显机制保留：汇合调用 #2 时把已发出的情绪写进指令，要求前后一致。
5. **v2 扮演提示词还原（2026-10-10）**：v3 重构时丢了一批 v2 业务验证过的扮演措辞，且把问答模式的硬要求误抄进了扮演规则，实测导致 NPC「伪人感」重。已按 v2 原文补回、不再随意删减（回归测试 `tests/orchestrator/test_roleplay_prompt.py`）：
   - system：情绪标签后补「请选择其中最合适的一种作为你当前的情绪立绘。」；「不要自己脑补不存在的设定」补回逃生口「无法把握的模糊地带可以略过或转移话题，不要自己乱加设定，以免出戏。」；任务硬约束补回「发布动机要自然融入对话；」并用回 v2 的完整拒绝句。
   - 共享 user core：检索为空时不再整块留白，改回 v2 兜底「（当前没有检索到任何上下文，你可以根据自己的设定自由发挥，但要保持合理。）」；历史块补回 v2 引导语（按有无摘要二选一），其中「在保持人物性格与情节连贯的前提下继续对话」是每轮一次、位置紧贴生成点的入戏提醒；无历史时整块不注入。
   - 末条 user：玩家发言之后按 v2 顺序追加**立绘文字说明**（`现在传入了你所扮演的角色「X」的肖像（不需要强行通过肖像内容开启话题）。`）与**上一轮情绪连贯提示**（`你之前的情绪是「X」。`，仅非「普通」时注入）。此前 v3 只发图片 part 不发说明，且 `current_emotion` 只用于挑立绘、从不进 prompt，等于每轮情绪从零起跳。
   - 删除：输出规则第 5 条的「陈述语气」——那是 v2 知识库问答助手模式的措辞（该模式明确要求「不要扮演 NPC 对白」），抄进扮演规则会压死疑问/感叹/口语。**未替换成任何新的语气硬要求**：泛泛而谈的「要说人话」类约束可能起反效果，具体措辞待另行研究。
   - `TASK_MERGE_INSTRUCTION` 的候选收尾句保留（结尾征询是否接取是流程硬要求），但标注为「仅供参考，不要照抄」，要求按 NPC 身份与当下情景用自己的话问——原先那 15 句现成模板会被弱模型直接抄，导致所有 NPC 一个腔调。
6. **路由工具化后的 prompt 再分层（2026-10-10，v3 再次重构）**：聊天主 Agent 与后台子 Agent 的身份要求、输出要求**彻底隔离**，各自只带自己那摊事：
   - system 层1（跨 NPC 恒定）：世界观 + 对话输出规则。层1 不再提路由——关闭 Agent 能力时没有任何路由工具，提了就是悬空指代；「路由轮不写台词」的例外由层2 的路由指南承担。
   - system 层2（单 NPC 恒定）：扮演约束 + meta 协议 + 同阵营表 + 路由指南（`build_routing_guide`，按有无待确认草案二分支）+ 任务发布硬约束 + 商店/切磋可行性 + appearance。
   - 原 `PREPARE_TOOL_GUIDE`（1229 字的任务选型规则）整体移交任务 Agent（`services/subagents/prompts.py`），聊天 system 因此瘦掉这一整块，前缀缓存命中率只受层2 影响。
   - meta 协议块只剩情绪与好感两个字段的说明，唯一的分支是 `agent_enabled`（关闭时不提路由）。
   - 汇合/过渡/收场调用共享 `build_merge_user_prompt`：**按条件拼接**的指令块（`task_merge_hint(task_type)` 按任务类型给不同说明要点、过渡语只给方向不给细节、confirm 收场禁止再问一次接不接）。
