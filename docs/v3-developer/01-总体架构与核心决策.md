# 01 · 总体架构与核心决策

> 本文是全部重构工作的架构依据。所有模块设计以此为准；后续各章是对应模块的细化。

---

## 1. 架构全景

```
玩家消息 (HTTP /api/ask, SSE)
   │
   ▼
TurnOrchestrator（每回合一个实例，纯 asyncio）
   │
   ├─ 1. 上下文装配（并行，目标 ≤300ms）
   │     ├─ NPC 状态（内存单例）
   │     ├─ 会话记忆（SQLite：近 N 条 + 滚动摘要）
   │     ├─ Tier-1 检索（1~3 次嵌入 + 矩阵乘 + BM25 RRF，≤150ms）
   │     └─ 立绘（manifest 查表 + 缓存；仅视觉模型）
   │
   ├─ 2. 聊天主 Agent（流式 LLM 调用 #1）
   │     首行 = meta JSON：情绪/好感/委派指令（act）
   │     其余 = NPC 对话正文（实时流给前端）
   │     ├─ 解析 meta → 立即发 mood 事件（前端先切立绘）
   │     ├─ act = task_draft / task_update / search
   │     │      → 立即启动后台子 Agent（asyncio.Task，fire-and-steer）
   │     ├─ act = task_confirm / task_cancel
   │     │      → 后端同步执行（快，<300ms），成功才放行正文
   │     └─ act = null → 正文流完即回合结束
   │
   ├─ 3. 等待/汇合（仅当有后台子 Agent）
   │     ├─ 子 Agent 已完成 → 汇合调用 #2：携带结果，NPC 详细说明
   │     ├─ 未完成但有中间结果 → 过渡语（只说一次、只说大概、不报数字）
   │     └─ 未完成无中间结果 → 等待（SSE 保活），拿到最终结果再汇合
   │
   └─ 4. 后处理：写记忆、更新好感、草案触碰计数、usage 落库、done 事件

后台子 Agent（与 2/3 并行运行）
   ├─ TaskRunner：LLM 工具循环（function calling）
   │     prepare_task_context → draft_agent_task / update_task_draft
   │     校验反馈聚合 + 自动修复 + 兜底，保证拟定能完成
   └─ SearchRunner：LLM 工具循环
         search_knowledge / search_items / search_stages → 结论摘要
```

关键形态：**玩家视角 NPC 始终是「一个人」**——先说话，再「想/查/写委托」（前端显示 tool_status/ui_hint），再开口给结果。前台并行只是为了消除空窗，不向玩家暴露多 Agent 存在。

## 2. D1：为什么废弃 LangGraph

问题清单证据：流式路径完全绕过编译图手写编排（B1）、四重防护全失效（B4）、死代码成堆（B6）、图框架还带入 langchain 依赖链（包体）。

新架构的控制流是「**一次流式调用 + 后台 asyncio 任务 + 检查点汇合**」，这是事件驱动模型，LangGraph 的静态图/超步模型表达它反而别扭（业界对此形态的答案是 fire-and-steer 后台子 Agent，见 `02-联网调研-Agent编排.md` §2）。HITL 靠「HTTP 轮次天然暂停 + SQLite 草案持久化」即可（现状已经如此，checkpointer 本来就没承担真正的中断恢复）。

**决策**：删除 `langgraph`、`langgraph-checkpoint-sqlite`、`langchain-openai`、`langchain-core`、`langchain-community` 依赖；删除 `services/agents/`、`services/agent_graph/`；自研 `services/orchestrator/`（预计 <800 行，单一真实路径）。

## 3. D2/D4：meta 行协议（聊天主 Agent 的产出格式）

聊天主 Agent **不被给予任何 function tools**（工具只给后台子 Agent）。它的全部「决策」通过**响应第一行的紧凑 JSON** 表达，优点：

- 一次调用同时产出情绪、好感变化、委派指令、对话正文——消灭 supervisor 路由 LLM（旧设计中它本身是一次完整 LLM 调用）。
- 与模型能力解耦：不支持 tools 的平台（如魔搭）聊天功能完全可用；思考模型「不支持强制 tool_choice」的约束（调研 §3.4）彻底绕开。
- 不再需要旧的正文字符串截断 hack（A4 整体删除）。

协议细节、解析器、容错见 `02-LLM接入层.md` §4。

## 4. D3：并行模型（fire-and-steer）

- 后台子 Agent = `asyncio.Task` + 结果 `asyncio.Queue`（progress/intermediate/final 三类消息）。不引入 Agent Protocol / 远程 deployment（那是多进程场景的方案，本地单用户过度设计）。
- steer 能力：本期内保留 `cancel()`（玩家连发新消息时取消旧后台任务）；`update`（补充指令）不实现，结构预留。
- 每会话同时最多 1 个活跃 TaskRunner + 1 个活跃 SearchRunner；同会话新回合到来时，未完成的旧子 Agent 一律取消（其副作用仅限内存与草案表，可安全丢弃；confirm/cancel 类已完成的写入不可回滚也不需要回滚）。
- 汇合规则（「中间结果只说一次话」「中间结果不报具体数字」等）是**硬性产品规则**，实现在 orchestrator，细则见 `03` §4。

## 5. SSE 事件契约（v3）

单条 SSE 连接，事件带类型。新契约（前端适配见 `09`）：

| event | data | 时机 |
|---|---|---|
| `meta` | `{emotion, favorability_change, favorability, relationship_level}` | 解析到 meta 行后立即发（正文之前） |
| `content` | `{delta}` | NPC 对话正文增量（纯台词，绝不含系统文本） |
| `tool_status` | `{tool, status, ui_hint}` | 后端工具执行进度（发布/取消等），`status ∈ running/success/failed` |
| `agent_status` | `{agent: "task"\|"search", phase, ui_hint}` | 后台子 Agent 阶段变化（拟定中/校验修复中/查询中…） |
| `system_notice` | `{text}` | 系统消息（替代旧 `{花括号}` 文本约定），如「任务草案已拟定，等待确认」 |
| `done` | `{session_id, usage{prompt_tokens, completion_tokens, cached_tokens?}}` | 回合结束 |
| `error` | `{code, message, retryable}` | 不可恢复错误 |

旧事件映射：`mood_update` → `meta`；`content` 保留但语义净化（只含台词）；`{...}` 花括号系统消息 → `system_notice`；`agent_status` 事件保留并真正展示；`done` 增加 usage。

## 6. Prompt 分层（保留并简化）

保留现有的「静态 system（L1 世界观 + 扮演约束）+ 共享 user core（RAG 块/会话状态/历史）+ 尾部指令」分层与前缀缓存对齐设计（实测 85~95%+ 命中，是有效资产），改动：

1. supervisor/决策层 prompt 全部删除；聊天尾部指令改为「meta 行协议 + 输出格式规则（【】动作、第三人称、禁半角括号等，沿用现状）」。
2. 后台子 Agent 使用**独立的小 prompt**（不含扮演约束/立绘/大部分世界观，只含任务规则或检索规则 + Skills 索引）——输入与聊天 prompt 差异很大，本就不该共享（用户决策）。Skills 渐进披露机制（list/read/read_file 三级）保留，仅子 Agent 持有。
3. 新增 `appearance` 形象描述块：npc_state_db.json 有该字段时恒常拼入聊天 prompt（无论是否发图），见 `07`。
4. 情绪回显机制保留：汇合调用 #2 时把已发出的情绪写进指令，要求前后一致。

## 9. 预留：游戏联动接口（只做 stub）

`services/gamebridge/interfaces.py` 定义 Protocol，不实现、不被调用：

```python
class GameBridge(Protocol):
    async def detect_running_game(self) -> GameProcessInfo | None: ...   # 进程/存档检测
    async def load_active_save(self) -> SaveInfo | None: ...             # 当前存档（身份/进度）
    async def task_scope_for_save(self, save_id: str) -> TaskScope: ...  # 按存档隔离任务
class DialogueAugmenter(Protocol):
    async def on_task_completed(self, save_id: str, task_id: int) -> None: ...  # 增量对话覆盖
```

意义：后续「游戏内启动/热更新/存档绑定/任务后对话联动」开发时，orchestrator 的上下文装配（`orchestrator/context.py`）是唯一注入点，现在就把 `save_info: SaveInfo | None` 作为上下文字段留好（默认 None）。
