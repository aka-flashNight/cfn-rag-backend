### 0.3 手册偏差回写（后续阶段以本文为准）

1. **confirm 需要一次轻量 LLM 调用生成发布文本**（02 §5 说 confirm 是"<300ms 纯后端操作"，但
   `confirm_agent_task` 的 title/description/get_dialogue/finish_dialogue 参数在 meta 行协议里
   没有携带通道）。实现：orchestrator 同步动作内先做一次非流式调用（purpose="subagent"、
   max_tokens=800）生成 JSON，LLM 失败回退模板文案（`prompts.fallback_confirm_args`）。
   该调用计入 usage，不计入「聊天主 Agent ≤3 次」预算（属同步动作内部）。09 §2.2 确认回合的
   实际时序为 `meta → tool_status(running) → tool_status(success) → content → system_notice → done`。
2. **SSE 端点保持 `/api/game/ask`**（09 §1 写 `/api/ask`）：现网前端（dist/）实际按
   `/api/game/sessions`、`/api/game/ask?stream=true` 调用，为兑现「端点不变」承诺保持现有前缀。
   前端适配（09）以事件契约为准，路径无变化。
3. **orchestrator 增加了第 5 个文件 `prompts.py`**（03 §1 只列 4 个）：聊天分层 prompt 资产
   （世界观/扮演约束/输出规则/汇合指令/confirm 参数生成）体量大，单独成文件。
4. **TaskRunner 的 dispatch 分组并行是「组间串行」**：同批 tool_calls 按 pipeline 序分组，
   组内 gather 并行、组间按序（draft→update 的草案状态继承需要）。同组可并行的只有
   skills 元工具等零依赖组合。
5. **llm/meta.py 修复一处 P1 遗留 bug**：无 meta 场景下，缓冲正文事件被排在 held
   usage/finish 之后，任何「finish 即终止」的转发方会**静默丢掉无 meta 回合的全部正文**。
   已修复为正文在前。
6. **memory/store.py 补旧库迁移**：已存在的 memory.db 是 v3 前的 schema（session_task_drafts
   无 bargain_count 列），启动时 ALTER TABLE + 从旧草案 JSON 回填，读取侧剥离内部字段。
7. **task_update 无草案时降级为重拟**：模型在有草案前误发 task_update（或草案已被
   confirm/cancel 清掉）时，orchestrator 按 note 作为 direction 启动 task_draft，不再报错卡死。
8. **V7 自动修复阈值口径**：05 §3「偏差 ≤±10%」实测按「超出量/被越过的区间端点」计算

9. **SearchRunner 无 `retrieve_fn` 时 search_knowledge 返回错误 JSON**（engine 未就绪/测试
   注入 None），模型脚本仍可作答；生产路径 assemble_context 恒注入。

### 0.4 SSE 实测序列样例（stub LLM，`python main.py` + curl）

纯聊天（09 §2.1）：
```
event: meta   data: {"emotion":"微笑","favorability_change":1,"favorability":30,"relationship_level":"熟悉"}
event: content data: {"delta":"诶，是"} × N（纯台词分块）
event: done   data: {"session_id":"...","usage":{"prompt_tokens":320,"completion_tokens":48,"total_tokens":368}}
```

发任务（09 §2.2，宽限内完成、无过渡语）：
```
meta → content(过渡话)×N → agent_status(task, drafting,「拟定委托中」)
     → agent_status(task, done) → content(草案详述+询问接不接)
     → system_notice(任务草案已拟定，等待确认) → done
```
（首轮实测还命中了修复链：draft 触发 V1 → `agent_status(task, repairing)` → 轮内未修复 →
`agent_status(task, drafting,「生成保底方案」)` → done——兜底路径在真实 HTTP 栈下工作正常。）

确认回合（09 §2.2）：
```
meta → tool_status(confirm_agent_task, running) → tool_status(confirm_agent_task, success)
     → content(确认话术)×N → system_notice(委托已发布) → done
```
（无草案时 confirm：`tool_status failed` + `system_notice(委托确认失败：当前没有待确认的委托草案)` + 补救话术正文。）

搜索（09 §2.4）：
```
meta → content(过渡)×N → agent_status(search, searching,「查资料中」)
     → agent_status(search, done) → content(详答) → done
```

## 3. 手册偏差回写（重要，后续阶段以本文为准）

1. **嵌入池化方式是 CLS，不是 mean pooling**（04 §1.3 有误）。`models/bge-small-zh-v1.5/1_Pooling/config.json` 实测 `pooling_mode_cls_token: true`，与既有语料嵌入行为一致。OnnxEmbedder 按 CLS + L2 归一化实现。
2. **optimum 导出方案不可用**（06 §3.2 的 `optimum[onnxruntime]`）：optimum 2.x 已把 ONNX 集成拆出主包且与 transformers 5.x 不兼容。改用 `torch.onnx.export`（TorchScript 导出器 `dynamo=False`，需关键字传参包装 BertModel），产物等价。另 torch 2.10 的 dynamo 导出器会把权重写外部文件、dynamic_axes 有约束问题，勿用。
3. **全量 int8 量化不达标**（04 §1.1 的 ~25MB 预估基于全量量化）：词嵌入表 int8 化后余弦仅 **0.964**，过不了 ≥0.99 硬门槛。最终 `quantize_dynamic` 限定 `op_types_to_quantize=["MatMul","Gemm"]` + `per_channel=True`（嵌入表保持 fp32），余弦 0.9952，模型体积 **54.6MB**（非 25MB）。exe 体积预算在 P8 打包时需按 55MB 口径复核。
4. **量化速度无差异**：int8_full 与 int8_linear 单查延迟 1.06/1.08ms、吞吐 309/320 条/s，噪声级持平；均比 fp32 快 1.6~1.8x（低于 Vespa 2.7~3.4x，短文本小批次正常）。选型只看质量与体积。
5. **嵌入吞吐的关键优化是 padding**：tokenizer 全局 padding 到批内最长会把多数批次拖到 512 token（p50 文本仅 ~50 token）。改为 token 长度降序分批 + 手工按批内最长 padding 后，整库嵌入 55s → 19s（216 条/s）。线程数用 ORT 默认即最优（扫过 2~20，手动降核单调变慢）。
6. **语料规模 4180 条**（调研时 4426 条，resources 语料已演进）；golden 集 expected_doc_ids 是旧 LlamaIndex uuid，新索引按文本精确映射仅 3/5 行可评。
7. **LLM 降级链的重试预算**：02 §2.2 写「同一请求最多 2 次真实调用」与 §3.2 的 a→b 剥参→裸请求链（最多 3 次）存在张力。实现取：网络重试仅首个请求享有（+1），降级链按 §3.2 字面执行（参数错最多 3 次）。
8. **fingerprint 覆盖目录**：data/dialogues、data/task、docs、data/intelligence、data/stages、data/items。若后续六类语料源扩展（如 07 的立绘 manifest），需同步加入。

## 4. int8 量化档位对比实验（evals/bench_int8_compare.py，2026-09-05）

三方自洽建库（各用各的模型编码索引与查询，与生产一致）+ 7 个真实场景 + 60 条随机自检索：

- 真实场景（物品/关卡/NPC 往事/任务/情报/世界观/loading）：**三方全部命中目标**（多为 #1），无阈值穿越失败。0.964 档不会「明显匹配不上」。
- 排序漂移（vs fp32）：0.964 档 top-10 重合率均值 **0.860**（完全一致仅 18%）；0.9952 档 **0.928**（38%）。
- 结论：0.964 档可用但是「噪声更大 + 阈值余量更小」的降级选项；现役 0.9952 档维持。若 P8 打包体积吃紧，可回退 int8_full（22.8MB）——去掉 export 脚本的 `op_types_to_quantize` 参数即可，实验脚本可复跑验证。
