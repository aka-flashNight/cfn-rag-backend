## 3. 手册偏差回写（重要，后续阶段以本文为准）

1. **嵌入池化方式是 CLS，不是 mean pooling**（04 §1.3 有误）。`models/bge-small-zh-v1.5/1_Pooling/config.json` 实测 `pooling_mode_cls_token: true`，与既有语料嵌入行为一致。OnnxEmbedder 按 CLS + L2 归一化实现。
2. **optimum 导出方案不可用**（06 §3.2 的 `optimum[onnxruntime]`）：optimum 2.x 已把 ONNX 集成拆出主包且与 transformers 5.x 不兼容。改用 `torch.onnx.export`（TorchScript 导出器 `dynamo=False`，需关键字传参包装 BertModel），产物等价。另 torch 2.10 的 dynamo 导出器会把权重写外部文件、dynamic_axes 有约束问题，勿用。
3. **全量 int8 量化不达标**（04 §1.1 的 ~25MB 预估基于全量量化）：词嵌入表 int8 化后余弦仅 **0.964**，过不了 ≥0.99 硬门槛。最终 `quantize_dynamic` 限定 `op_types_to_quantize=["MatMul","Gemm"]` + `per_channel=True`（嵌入表保持 fp32），余弦 0.9952，模型体积 **54.6MB**（非 25MB）。exe 体积预算在 P8 打包时需按 55MB 口径复核。
4. **量化速度无差异**：int8_full 与 int8_linear 单查延迟 1.06/1.08ms、吞吐 309/320 条/s，噪声级持平；均比 fp32 快 1.6~1.8x（低于 Vespa 2.7~3.4x，短文本小批次正常）。选型只看质量与体积。
5. **嵌入吞吐的关键优化是 padding**：tokenizer 全局 padding 到批内最长会把多数批次拖到 512 token（p50 文本仅 ~50 token）。改为 token 长度降序分批 + 手工按批内最长 padding 后，整库嵌入 55s → 19s（216 条/s）。线程数用 ORT 默认即最优（扫过 2~20，手动降核单调变慢）。
6. **语料规模 4180 条**（调研时 4426 条，resources 语料已演进）；golden 集 expected_doc_ids 是旧 LlamaIndex uuid，新索引按文本精确映射仅 3/5 行可评。
7. **LLM 降级链的重试预算**：02 §2.2 写「同一请求最多 2 次真实调用」与 §3.2 的 a→b 剥参→裸请求链（最多 3 次）存在张力。实现取：网络重试仅首个请求享有（+1），降级链按 §3.2 字面执行（参数错最多 3 次）。
8. **fingerprint 覆盖目录**：data/dialogues、data/task、docs、data/intelligence、data/stages、data/items。若后续六类语料源扩展（如 07 的立绘 manifest），需同步加入。

## 4. int8 量化档位对比实验（evals/bench_int8_compare.py，2026-09-05）

三方自洽建库（各用各的模型编码索引与查询，与生产一致）+ 7 个真实场景 + 60 条随机自检索：

- 真实场景（物品/关卡/NPC 往事/任务/情报/世界观/loading）：**三方全部命中目标**（多为 #1），无阈值穿越失败。0.964 档不会「明显匹配不上」。
- 排序漂移（vs fp32）：0.964 档 top-10 重合率均值 **0.860**（完全一致仅 18%）；0.9952 档 **0.928**（38%）。
- 结论：0.964 档可用但是「噪声更大 + 阈值余量更小」的降级选项；现役 0.9952 档维持。若 P8 打包体积吃紧，可回退 int8_full（22.8MB）——去掉 export 脚本的 `op_types_to_quantize` 参数即可，实验脚本可复跑验证。
