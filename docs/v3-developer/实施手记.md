## 0.S 本窗口（检索链结构重构：route_search 直接做检索第一步＋常规检索不委派子 Agent，2026-10-17）

> 承接 0.R 的诊断。作者定稿：**不做过渡语，改结构**。本轮已施工、离线测试全绿；
> 未跑真机（按「发现代码问题先改好再测」的规则，真机留到作者确认后）。

### 0.S.1 定稿口径

- `route_search` 不再只是「声明要查」，而是承担检索子 Agent 的**完整第一步**：
  聊天主 Agent 在路由参数里直接给出 `keywords` 与 `sources`，编排层用代码完成第一轮检索。
- 参数：`keywords`（必填，≤80 字）；`sources`（`knowledge` / `items` / `stages`，可多选，
  不填或含 `all` 表示全部，多选取并集）；`deep_search`（默认 `false`，描述里明确**不推荐开启**）；
  `query`（非必填，仅 `deep_search=true` 时填写，只给后台子 Agent 看）。
- **常规检索（deep_search=false）**：不委派子 Agent。编排层预取后，把结果块直接拼进
  下一轮聊天调用（路由轮 + 续写轮＝**2 次模型调用**）。续写轮不带任何 tools（机制闸）。
- **深度检索（deep_search=true 且有 query）**：预取结果与聊天 Agent 已有的 Tier-1 材料
  一起交给检索子 Agent（已有在上、新查在下）；子 Agent 自己决定继续补查还是直接总结。
  结论回到汇合轮，由聊天 Agent 以 NPC 口吻讲出。
- `deep_search=true` 但没填 `query`：按常规检索处理并留 warning（不做隐式深度）。

### 0.S.2 调用结构对比（回答「第 4 轮为什么触发」）

旧检索一轮固定 4 次调用：路由（静默）→ 子 Agent 调工具 → 子 Agent 出结论 → 汇合轮讲给玩家。
**第 4 轮不是多余的一轮**——路由轮按契约零台词，必须有一次「拿到结果后开口」的调用；
真正重复的是第 3 轮（子 Agent 结论）与第 4 轮（把同一段信息改写成口吻台词）。
新常规检索把这两步合成一次：路由轮 → 带结果块直接续写，共 2 次调用；
深度检索为 路由 → 子 Agent 1~N 轮 → 汇合，共 3~N+2 次。

### 0.S.3 截断：改前 vs 改后

改前（三条独立硬切，互不知情）：

1. `execute_search_knowledge` 把格式化后的结果硬切 `[:2000]`（`services/agent_tools/handlers.py`）；
   0.P 走查里两次工具返回都撞到 2000 上限。
2. `search_items` 最多 10 条、`search_stages` 最多 8 条，**按数据顺序**取，不看相关度。
3. 子 Agent 结论 `_FINDINGS_MAX_CHARS=400` 硬切；提示词也写 400，模型多写一点就被砍。

改后（`services/orchestrator/search_prefetch.py`）：

- 分类型预算：knowledge 3600 字、items 1200 字、stages 1200 字，合计约 6000 字；
  类型内不足不向其他类型借额度。
- knowledge：沿用 Tier-1 管线（池阈值＋top_k），先按 dense 相对下限（本类型最高分的 35%）
  筛掉明显低相关项，再按融合分排序依次填充；单条正文上限 800 字；与聊天 Agent 已有的
  Tier-1 结果**按节点 id 去重**，避免同一段资料进两次 prompt。
- items / stages：与 `search_items` / `search_stages` 同语义（名称/区域子串匹配），
  按「完全相等 > 前缀 > 子串」排序；已有实体排除；单行 320 字。
- 预算装不下时截断当前条目并停止；剩余不足 120 字则不再塞半句。
- 深度检索结论：提示词仍要求 400 字，后端放宽到 `_FINDINGS_MAX_CHARS=1000`，
  允许模型自然收尾，不再「生成了又丢掉」。

### 0.S.4 提示词逐字变更

`route_search` 描述（改后）：

> 直接检索后台资料库：需要查证世界观设定、角色往事、关卡或物品的具体信息才能回答玩家时调用。
> keywords 写清要查什么；sources 选定检索范围（knowledge=世界观/剧情/角色/任务对话，items=物品，stages=关卡），
> 不填或填 all 表示全部，多个范围取并集。deep_search 默认 false，不推荐开启：常规检索通常已经足够；
> 只有一次检索明显不够、需要多轮深入核对时才设为 true，并同时填写 query（只给后台深入检索使用）。
> 开启后会多轮检索，耗时和花费更高。本轮**只发这个工具调用，不要输出任何台词**：
> 检索结果会直接回到你手上，那时你以自己的口吻讲给玩家；查不到就自然带过，不要编造设定。

schema：`keywords`（string, maxLength 80，唯一必填）、`sources`（array，enum
`knowledge/items/stages/all`）、`deep_search`（boolean）、`query`（string, maxLength 40）。

`SEARCH_RUNNER_SYSTEM`【工作方式】改为：user 里已给「已有资料」与「本轮已检索资料」两批，
先通读，够就直出结论、不再调工具；不够最多补查 2 次，不重复检索已给内容；查不到直说。
【最终输出】保持 400 字要求与出处标注。

`search_runner_user_prompt` 新增两段（按此顺序）：
`【已有资料（主对话 Agent 本轮上下文里已有，可直接采用，不必重复检索）】`、
`【本轮已检索资料（按查询要点预取，可直接采用；不够时再补查）】`。

### 0.S.6 边界与已知取舍

- `sources` 用数组而非单选，是作者「某一项或全部」的超集；`all` 混在多项里也按全部处理；
  未知值忽略，归一化后为空则回落全部。
- items/stages 只做名称/区域子串匹配（与现有工具一致，结果可预期）；自由文本语义查询走
  knowledge 池。
- 深度检索只在路由时决定，回合中途不升级；缺 `query` 时降级为常规检索。
- 深度检索会出现两帧 `agent_status(search, searching)`（编排层预取一帧、子 Agent progress
  一帧），相位相同、前端表现为同一条进度，不影响契约；`done/failed` 只由子 Agent 终态发一次。
- 预取是本地 ONNX 检索，不产生 API 费用；与 Tier-1 去重只省 prompt token。
- 预取日志一行：`预取检索完成：keywords=… sources=… knowledge=… items=… stages=… chars=…`。

### 0.R.4 方案（按性价比排，未施工）

- **方案一 参数扩容＋代码预取（推荐，收益最大）**：`route_search` 参数从 `{query}` 扩成
  `{query, keywords:[1~3], want_items, want_stages}`；编排层拿到参数后**用代码并发跑检索**
  （retrieve_tier1 / search_items / search_stages 都是纯函数，不经模型），结果直接拼进子 Agent 第 1 条 user。
  子 Agent 只剩「读资料＋出结论」一轮。调用 4→3，静默期 16.76s→约 11.7s，整轮 32.2s→27s 上下。
  代价：路由轮多吐几十字符（它本来 8.46s 只吐 44 token，几乎不加时间）＋ `route_search` 描述要改（属提示词，需逐字回报）。
- **方案二 复用 Tier-1 命中材料**：与方案一同一处动手（预取本就是 Tier-1 的复用），也可单独做。
  顺带压一条 0.P.4 的老缺陷（常驻 Tier-1 块实体覆盖不足 → 把真实设定说成没听过）。
- **方案三 结论不截断**：`_FINDINGS_MAX_CHARS` 400→约 700 或按剩余预算给。改动最小，先止住「生成了又丢掉」。
- **方案四 乐观并行预检索**：发路由轮的同时用玩家原话先跑深检索，命中 search 就用、没中就丢。
  省的只是那 2s 工具执行，复杂度不划算，**暂不做**。
- **方案五 子 Agent 直接口吻化、砍掉汇合轮**：省 4.99s，但情绪 meta、好感语气、空结果兜底、

### 0.Q.1 说话人「玩家」归一成 `$PC`（`services/dialogue/editor.py::_merge_lines`）

模型交回的行里玩家常被写成中文「玩家」。AS2 只认 `$PC` 占位符（称号槽与立绘都按它取），
写成「玩家」既过不了白名单、即便放过也不会被游戏侧解析，所以后端在**进白名单之前**把它换掉：
`_merge_lines` 是日常改组、日常新增组、任务文本三条路径的共同入口，一处生效覆盖全部；
校验闸本体与打回话术一字未改（越界说话人照旧整组打回）。**提示词侧没动**——0.P.7 待定 4 问的
「要不要在提示词里硬要求 `$PC`」仍未拍板，本批只做「后端兜住」这一半。

走查取证的成因就在这一条：16:20 那轮触发三提交了三组，编号 8 与编号 12 两组确实是在改旧台词，
都因为第 2/5 行说话人写成「玩家」被整组打回，最后只剩新增组落盘——「只会 append 新组」的一半原因是它。

### 0.Q.2 子 Agent usage 三段接力（不落空 ＋ 后端留痕）

1. **漏斗留痕**：`LLMClient.chat` 与 `chat_stream` 每次真实调用各落一行 INFO
   （`purpose / model / stream / 耗时 / 首字 / prompt / completion / cached`）。这是全项目唯一落
   usage 日志的地方，后台子 Agent 与**脱离回合的对话修改 worker**都经过它——事后查缓存命中率
   只读 `cfn-rag.log`，不必再挂 0.P.5 那种类层探针。流式那行**写在 finish 事件之前**：下游见到
   finish 就 return、生成器随即关闭，写在后面等于不写（已单测锁住）。
2. **子 Agent 带上来**：`SubagentBase` 每轮把 `result.usage` 原样追加进 `usage_rows`，四个终态出口
   （工具终态／耗尽兜底／文本终态／failed）统一经 `_with_usage` 随 `final`／`failed` 载荷上交。
   本层不求和——累计口径属 SSE 契约层的 `accumulate_usage`，反向依赖会绕成循环导入。
3. **回合并入**：`MergeCoordinator._drain` 在收到终态事件的那一刻按到达时序逐行并入
   `outcome.usage`，并**从业务载荷里摘掉 `usage_rows`**——留着会混进汇合提示词的结果块。
   `turn.py` 原有的 `accumulate_usage(self._usage, outcome.usage)` 不动，done 事件的 `calls`
   因此从「只含聊天两次」变成含子 Agent 全程；实测一轮检索原先少计 prompt 25.5%／completion 56.0%。

对话修改子 Agent 由全局串行 worker 驱动、不进任何回合，它的 usage **只进日志漏斗**（第 1 段），
不冒充某个回合的明细。

### 0.K.2 幂等口径修订（本批两处，游戏仓 §4.7 为同源正文）

**缺陷**：`POST /api/integration/task-completed` 的幂等去重只问「`(slot_key, task_id)` 有没有记录」，
不看状态。自动委派把「发布时没挂对话重写标记」的任务判成 `dismissed` 后，这条留痕把部分唯一索引
永久占住；而聊天侧兜底调用（专为漏挂标记的任务准备的**唯一**补救路径）走的是同一个键，
于是永远回「已委派过，静默跳过」。

1. **占位口径改为「派出过或在途」**：`services/memory/store.py` 新增元组常量
   `DIALOGUE_JOB_CLAIMED_STATUSES`（`received` / `judging` / `delegated` / `generating` / `written` / `skipped`），
   由其派生 SQL 片段常量 `DIALOGUE_JOB_CLAIMED_SQL`；**部分唯一索引的 `WHERE` 谓词**与**插入前预检查**
   都拼这同一片段，两处不会漂移。`dismissed`（不够格，从没派出过）与 `failed`（没派出去／派出后跑坏）
   **不占位**，留痕仍照常落库可审计。
2. **权威发布 NPC 解析前移**：`services/dialogue/delegation.py` 改成先读任务详情并把权威发布 NPC 落地，
   **再**判标记。完成事件允许只带任务 id（游戏侧不必重复给 NPC），原顺序在标记检查处就 return，
   被驳回的留痕行写不上 NPC。对外提示句一字未改。

**为什么放开重试不会失控**（写用例时逐条核过，不需要再加「软闸」）：冷却窗与每会话委派上限
**都只数 `delegated_at IS NOT NULL`**，`dismissed` / `failed` 不占额度；`worker.py` 里「玩家切存档即中止」
落的是 `failed`，因此同一任务能重派。

**接受的代价**（都写进代码注释与文档，不写兼容）：同一已完成任务反复推完成事件会**每次追加一条
`dismissed` 留痕**（零模型调用）；在 `received` / `judging` 阶段进程崩溃＝该任务被**永久占位**。

**手动清残留**：实测本机两个 `memory.db`（游戏仓 `tools/` 与后端仓 `tools/`）都还没有 `dialogue_jobs` 表，
`DROP INDEX` 那步是空操作。**代码侧按裁定不写任何版本内迁移。**

## 3. 手册偏差回写（重要，后续阶段以本文为准）

1. **嵌入池化方式是 CLS，不是 mean pooling**（04 §1.3 有误）。`models/bge-small-zh-v1.5/1_Pooling/config.json` 实测 `pooling_mode_cls_token: true`，与既有语料嵌入行为一致。OnnxEmbedder 按 CLS + L2 归一化实现。
2. **optimum 导出方案不可用**（06 §3.2 的 `optimum[onnxruntime]`）：optimum 2.x 已把 ONNX 集成拆出主包且与 transformers 5.x 不兼容。改用 `torch.onnx.export`（TorchScript 导出器 `dynamo=False`，需关键字传参包装 BertModel），产物等价。另 torch 2.10 的 dynamo 导出器会把权重写外部文件、dynamic_axes 有约束问题，勿用。
3. **全量 int8 量化不达标**（04 §1.1 的 ~25MB 预估基于全量量化）：词嵌入表 int8 化后余弦仅 **0.964**，过不了 ≥0.99 硬门槛。最终 `quantize_dynamic` 限定 `op_types_to_quantize=["MatMul","Gemm"]` + `per_channel=True`（嵌入表保持 fp32），余弦 0.9952，模型体积 **54.6MB**（非 25MB）。exe 体积预算在 P8 打包时需按 55MB 口径复核。
4. **量化速度无差异**：int8_full 与 int8_linear 单查延迟 1.06/1.08ms、吞吐 309/320 条/s，噪声级持平；均比 fp32 快 1.6~1.8x（低于 Vespa 2.7~3.4x，短文本小批次正常）。选型只看质量与体积。
5. **嵌入吞吐的关键优化是 padding**：tokenizer 全局 padding 到批内最长会把多数批次拖到 512 token（p50 文本仅 ~50 token）。改为 token 长度降序分批 + 手工按批内最长 padding 后，整库嵌入 55s → 19s（216 条/s）。线程数用 ORT 默认即最优（扫过 2~20，手动降核单调变慢）。
6. **语料规模 4180 条**（调研时 4426 条，resources 语料已演进）；golden 集 expected_doc_ids 是旧 LlamaIndex uuid，新索引按文本精确映射仅 3/5 行可评。
7. **LLM 降级链的重试预算**：02 §2.2 写「同一请求最多 2 次真实调用」与 §3.2 的 a→b 剥参→裸请求链（最多 3 次）存在张力。实现取：网络重试仅首个请求享有（+1），降级链按 §3.2 字面执行（参数错最多 3 次）。
8. **fingerprint 覆盖目录**：data/dialogues、data/task、docs、data/intelligence、data/stages、data/items。若后续六类语料源扩展（如 07 的立绘 manifest），需同步加入。

## 4. int8 量化档位对比实验（evals/bench_int8_compare.py，2026-09-05）

三方自洽建库（各用各的模型编码索引与查询，与生产一致）+ 7 个真实场景 + 60 条随机自检索：

- 真实场景（物品/关卡/NPC 往事/任务/情报/世界观/loading）：**三方全部命中目标**（多为 #1），无阈值穿越失败。0.964 档不会「明显匹配不上」。
- 排序漂移（vs fp32）：0.964 档 top-10 重合率均值 **0.860**（完全一致仅 18%）；0.9952 档 **0.928**（38%）。
- 结论：0.964 档可用但是「噪声更大 + 阈值余量更小」的降级选项；现役 0.9952 档维持。若 P8 打包体积吃紧，可回退 int8_full（22.8MB）——去掉 export 脚本的 `op_types_to_quantize` 参数即可，实验脚本可复跑验证。
