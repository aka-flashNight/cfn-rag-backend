## 2. 校验聚合（validator.py 重构）

### 2.1 新返回结构

```python
@dataclass
class ValidationIssue:
    rule: str                    # "V1".."V11"
    field: str                   # 出错字段
    message: str                 # 人话描述
    root_cause: str              # 后端定位的根因（如"物品'猫爪爪'不在游戏数据中，是否想表达'猫爪'？"）
    fix_hint: str                # 具体修正动作（如"把 submit_items[0].name 改为'猫爪'，数量保持 3"）
    candidates: list[str] = field(default_factory=list)   # 可选项（≤10 条）
    auto_repairable: bool = False

@dataclass
class ValidationReport:
    issues: list[ValidationIssue]          # 一次跑完所有规则，全量收集（修 D1）
    @property
    def ok(self) -> bool: return not self.issues
```

执行方式：`validate_task_draft(draft, mode="full"|"incremental", changed_fields=None)` 跑完全部（或增量关联的）规则后统一返回。V9（雷同）维持 warning 不阻塞。

### 2.2 各规则的反馈增强（修 D3）

| 规则 | 现状 | 增强 |
|---|---|---|
| V1 物品存在 | 有提示 | + **模糊匹配候选**（编辑距离/子串，≤5 个真实物品名） |
| V2 数量 | 给 allowed_range | + 直给「当前 X，需调整到 [a,b]，建议值 m」 |
| V3/V4/V5 关卡 | 只给数值 | + 附带玩家当前进度下**可用关卡候选清单**（从 prepare 候选里取，≤10） |
| V6 前置任务 | 合法 | 保持 |
| V7 价值 | 给区间 | + **直给差额数值**（"当前总值 2150，超出上限 2000，需减少 ≥150；可把'金币'从 800 降到 650"） |
| V8 奖励类型 | 给 reason | + 当前 NPC 合规奖励类型清单（商店 ∪ 历史奖励类型） |
| V10 装备等级 | 合法 | + 当前阶段允许的等级上限与该物品可选替代品 |
| V11 重名 | 合法 | 保持（且自动可修，见 §3） |

## 3. 自动修复层（repair.py，新增）

`validate` 之后、`draft_agent_task` 落库之前执行：

```python
def auto_repair(draft: dict, report: ValidationReport
               ) -> tuple[dict, list[str], ValidationReport]:
    """返回 (修复后草案, 修复说明列表, 剩余报告)"""
```

| 场景 | 修复动作 |
|---|---|
| V7 总值偏差 ≤ ±10% | 按单价明细等比缩放一个奖励项数量到区间内最近值，记 note |
| V2 数量越界 | clamp 到 allowed_range 最近端点 |
| V10 装备超等级 | 降级到阶段上限（若有同物低级版本）否则移除该项并 note |
| V11 重名 | 保留先出现项，去重并 note |
| V1/V3/V4/V5/V6/V8 | **不可自动修**（存在性/合规性，必须模型重新选择） |

修复说明（如「已自动微调：奖励'金币'数量 800→650」）随工具结果返回给模型，并记入草案 `repaired_notes`，最终 confirm 时可一并展示。原则：**后端只动数值，不替模型做选择**。

## 4. draft_agent_task 新流程

```
LLM 提交草案
 → validate(full)
 → ok → 存草案 → final
 → 有 issue → auto_repair（**数值类全修，无幅度门槛**：V7 按取整阶梯调奖励
   [金币/经验值 5000、区间上限<20000 按 1000、K点 100、其他物品 1]；V2 clamp；
   V10 降级/移除；V11 去重）→ 复审 ok → 存草案（带 repaired_notes）→ final
 → 仍有选择类 issue（V1/V3~V6/V8，后端不可修）→ 返回 ValidationReport 全量 JSON
   （root_cause + fix_hint + candidates + auto_repaired 已微调说明）
     + 当前草案快照（修 D4）→ TaskRunner 下一轮修正（draft 单独限 3 次）
 → 轮限耗尽 → 兜底：最后草案终微调，模型从未交出完整草案才重造（§5，池子已排除
   agent_tasks/mercenary_tasks 来源）
```

## 5. 后端兜底（fallback_draft，新增）

**兜底的第一选择是对最后一次草案做终微调**（同 §4 的 auto_repair，含 V7 取整阶梯），
只有当模型从始至终未交出结构完整草案时才走重造式兜底：

```python
def build_fallback_draft(direction, ctx) -> dict:
    """用核心池候选（已排除 agent_tasks/mercenary_tasks 来源，活动物品不进池），
    按最保守规则构造合法草案；产出标记 fallback=True，100% 通过校验。"""
```

兜底草案照常进入 HITL（玩家可见可拒）。这是「不能再把模型卡失败」的最终保险。

## 6. confirm / cancel（供 orchestrator 同步调用）

- `confirm_agent_task` 保持「合并标题说明对话 → 全量校验 → 原子写」不变；校验失败时同样先走 auto_repair 再报错（极端情况下草案存续期玩家进度变化导致回归，S5）。
- 这两个操作是同步快操作（<300ms），由聊天主 Agent 的 meta.act 直接触发（03 §4.2），不经子 Agent。
- 失败时返回结构化原因供「补救调用」生成 NPC 话术。

## 7. TaskDirection 的传递

聊天主 Agent meta 行的 `direction/reward_hint/note` → TaskRunner prompt 中的「任务方向（严格遵守）」块。TaskRunner 的规则：

1. direction 中明确的任务类型/目标物/关卡**不得违背**；候选不足时才允许偏离，且必须在 final payload 的 `deviation_note` 中说明（供 NPC 汇合时解释）。
2. reward_hint 优先满足；与 V7/V8 冲突时以校验为准并在 note 说明。

## 8. 测试要求（P5 验收）

1. 聚合校验：构造同时违反 V1+V7+V11 的草案，断言一次返回 3 条 issue。
2. 自动修复：V7 偏差 5%、V2 超 1 个、V11 重名，各断言修复后过检且 note 正确。
3. 反馈质量：V1 断言 candidates 含模糊匹配的正确物品；V7 断言 fix_hint 含具体差额数字。
4. 兜底：mock 模型连续 4 轮返回非法草案 → 断言 final 为 fallback 草案且通过全量校验。
5. confirm 回归：草案落库后篡改进度再 confirm → 走 auto_repair 或结构化失败，不崩溃、不写半截文件。
6. 原子性：写入中强杀进程（集成测试可跳过，人工验证一次）→ agent_tasks.json 不损坏。
