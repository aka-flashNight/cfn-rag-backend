## 1. 项目定位与功能全景

CFN-RAG Backend 是面向游戏 Crazy Flash Night (CFN) 的后端服务，核心功能：

1. **NPC 角色扮演对话**：基于游戏资源（对话 XML、任务 JSON、世界观 PDF/DOCX、情报 TXT、loading 文案、物品/关卡结构化数据）做 RAG 检索，以指定 NPC 身份与玩家对话。
2. **好感度 / 情绪系统**：每轮对话产出 `favorability_change`（-5~5）与 `emotion`（NPC 可用情绪列表内），驱动立绘切换与关系等级（陌生/熟悉/朋友/生死之交，0-100 好感区间映射）。
3. **任务发布 Agent**：对话中 NPC 可发布委托任务，流程为 `prepare_task_context → draft_agent_task →（玩家确认/讨价还价）→ confirm_agent_task`，最终原子写入 `agent_tasks.json` / `agent_text.json`。
4. **会话管理**：SQLite/Postgres 存会话、消息、摘要（达到间隔后 LLM 生成滚动摘要）、任务草案。
5. **双 Profile**：`CFN_PROFILE=local`（SQLite + LlamaIndex 本地向量 + 内存缓存）与 `server`（Postgres + Qdrant + Redis + arq Worker + Prometheus）。
6. **分发形态**：PyInstaller 单文件 exe（实测仓库内 `CFN-RAG-v2.9.9.exe` 为 357MB），`launcher.py` 启动后端 + 前端静态服务 + 本地反代（`/api/*` → `127.0.0.1:7077`，SSE 流式转发）。
7. **附属物**：MCP Server（游戏数据查询）、Ragas/检索层评估体系、Locust 压测、K8s/Helm 部署清单。

技术栈（requirements.txt 实际安装）：FastAPI + LangGraph 1.1.9 + LlamaIndex 0.14.16 + openai SDK 2.26 + HuggingFaceEmbedding（经 transformers 5.3 + **torch 2.10**）+ rank_bm25 + Redis/Qdrant/SQLAlchemy/arq/ragas/locust/fastmcp 等（全部同装，venv 实测 1.5GB）。

> 维度勘误：嵌入模型 bge-small-zh-v1.5 实际输出 **512 维**（本地 `models/bge-small-zh-v1.5/config.json` 实测 `hidden_size: 512`）；README 与 `QdrantBackend`/迁移脚本中多处写作 384 维（384 是英文版 bge-small-en-v1.5 的维度），详见问题清单 C7。

## 2. 请求主链路（一条玩家消息的完整旅程）

入口 `api/game_api.py` `/api/ask`（stream=true 走 SSE）：

```
ensure_embed_model_ready() → 等嵌入模型加载完
apply_proxy_config(payload.proxy_url)  → 直接改进程级 HTTP_PROXY/HTTPS_PROXY 环境变量
service.ask / ask_stream
  ├─ _use_agent_graph?（agent_enabled≠false 且 progress_stage∈[1,7]）
  │    ├─ 是 → LangGraph 管线（非流式：graph.ainvoke；流式：手动编排，见 §4.3）
  │    └─ 否 → legacy 单次 LLM 路径（_ask_legacy / _ask_stream_legacy）
```

`NPCManager.load()` 作为 FastAPI 依赖**每个请求重新执行**：重新读 `npc_state_db.json` 全量 JSON 并解析。

### 2.1 上下文准备（prepare_context_node / _prepare_ask_context）

- 读取 NPC 静态状态（阵营/称号/情绪列表/切磋关卡/商店）；
- RAG 多路检索 `_retrieve_context`（§5）在 `asyncio.to_thread` 中同步执行；
- 从用户输入中**子串匹配**提及的其他 NPC（名称/阵营/称号+别名表），拼「其他角色设定」块；收集同阵营 NPC 列表；
- 拼对话历史（近 N 条 + 滚动摘要）；
- 立绘处理：按 `NPC名#情绪.webp/png → NPC名#普通 → profiles头像` 三级回退找图；**每次请求**用 PIL 重新裁剪+缩放+WebP 编码 + base64（无缓存）。

### 2.2 非流式 Agent 路径（ask）

`services/agents/graph.py` 编译主图（带 Checkpointer，thread_id=session_id）：

```
prepare_context → supervisor（路由）→ query_worker / task_worker / dialogue_worker → finalize → END
```

- worker 完成后**静态边**直接进 dialogue_worker，不再回 supervisor（单跳路由设计）。
- dialogue_worker 产出 final_reply → finalize（=post_process_node：写消息、更新好感度、持久化草案）。

### 2.3 流式 Agent 路径（ask_stream）——手动编排

`game_rag_service._ask_stream_with_graph` **不使用**编译图，而是手动顺序调用节点：

1. `prepare_context_node`
2. `supervisor_node`（非流式 LLM 路由）
3. 若有 `interim_reply`：`_simulated_content_chunks` 伪流式（6 字/30ms sleep）推给前端；
4. query/task worker 单独 `.astream(stream_mode="values")` 逐状态吐 `_ui_events` 与 `_system_prefix_text` 增量；
5. dialogue 阶段改写 state（清 `_system_prefix_text`、写 `_streamed_prefix_for_llm` 快照）后调用独立协程 `generate_response_stream` 输出真 token 流；
6. `parse_mood_node`（同步）+ `post_process_node`，最后发 `done` 事件。
- 注释自述原因：整图 astream 时子图内部更新会在主图侧聚合，「多个事件挤成一坨才到前端」。
- 以「实际发给前端的 content 流」为唯一事实来源拼 `final_reply`（reply_fragments 累加）。

### 2.4 Legacy 路径（agent_enabled=false 或 progress_stage 缺失）

单次 LLM 调用（带 `update_npc_mood` 工具），无工具轮、无任务能力。流式版含 `_TRUNCATE_PREFIXES` 截断逻辑（§6.3）。

## 3. LLM 调用层（services/llm_client.py）

### 3.1 两个入口

- `call_llm`：非流式，`chat.completions.create(**kwargs)`；`tools` 参数存在时传入（即非流式+tools 可共存）。
- `call_llm_stream`：流式，同样支持 `tools`（流式中增量聚合 tool_calls deltas）。

### 3.2 特殊逻辑

- **流式中解析部分 JSON**：`call_llm_stream` 在 tool_call delta 聚合过程中，每当 `update_npc_mood` 这个特定工具的参数 JSON 「已完整可解析」，就 yield 一条 `("mood_update", {...})` 事件（每 index 最多一次）——为的是前端提前切换立绘。工具名**硬编码在通用客户端层**。
- **死代码**：`prefix_parts: List[str] = []` 永远为空，`prompt_prefix` 逻辑空转（两个入口各一份）。
- 多模态：文本 part 在前、图像 part 在后（注释说明为缓存对齐）。
- **每次调用新建 `AsyncOpenAI` 客户端**（无连接复用）；主路径无超时/重试参数（仅 evals 专用路径设置了 900s 超时）。
- 不传 `temperature` / `max_tokens` / `tool_choice` / `response_format` / `parallel_tool_calls`；无 usage 统计；无 reasoning/thinking 字段处理。

### 3.3 错误降级（5 处复制的组合回退矩阵）

`npc_mood_agent.py` 定义：
- `is_image_unsupported_error`：按错误消息关键词（image_url / vision / multimodal / not support…）判断；
- `is_tools_unsupported_error`：**status_code ∈ (400, 422) 即判定为「不支持工具」**，另有关键词匹配。

组合回退（带图+工具 → 无图+工具 → 带图无工具 → 无图无工具）在以下 5 处**各自复制**一份：
1. `game_rag_service._ask_legacy`
2. `game_rag_service._ask_stream_legacy`（含「已流式输出过正文就不再重试」的判断）
3. `agent_graph/nodes.py decision_node`（仅 tools 一层）
4. `agent_graph/nodes.py generate_response_node`
5. `agent_graph/nodes.py generate_response_stream`（含 `streamed_model_content` 防重）

## 4. 多 Agent 实现

### 4.1 Supervisor（services/agents/supervisor.py）

- 单次非流式 LLM 调用（tools=None），**纯 prompt 约束 JSON 输出 + 正则兜底解析**（`_JSON_RE` 抓 `{...}`；失败兜底 route=dialogue）。docstring 声称「尝试 response_format=json_object」，代码实际**未使用** response_format。
- 输出：`route ∈ {query, task, dialogue, end}` + `reason` + 可选 `interim_reply`（≤80字）+ `mood`（emotion + favorability_change，**在路由阶段就由 supervisor 决定**，等价于代替 dialogue/工具上报情绪）。
- 规则短路 `_rule_route_pending_draft`：有待确认草案时，用**硬编码中文正则**匹配接受/拒绝/议价短语直接路由（省一次 LLM）。
- 防护：MAX_HOPS=6、per-worker 上限 3、连续失败 2 次拉黑、`token_budget_spent` 40k 熔断。**但 `token_budget_spent` 除初始化为 0 外从未被任何节点累加**，该熔断实际永远不触发。
- LLM 失败时回退 route=dialogue。

### 4.2 Worker 子图（services/agents/workers.py）

- Query/Task worker = `entry → decision ↔ tool_executor → exit` 循环子图（MAX_WORKER_TOOL_ROUNDS=4），task worker 另有「终态即退出」硬阻断（draft_created/updated、confirmed、cancelled 出现即退出，防止同轮 draft→confirm 连发）。
- 工具白名单（tool_scopes.py）：
  - query: search_knowledge / search_stages / search_items + system 元工具（list_skills/read_skill/read_skill_file）
  - task: prepare_task_context / draft / update / confirm / cancel + search_stages/search_items + system
  - dialogue: update_npc_mood + system（但生成轮在多 Agent 模式下**不传任何工具**，见 §4.4）
- worker exit 节点做：连续失败计数与黑名单、HITL 状态机（draft_created/updated → awaiting_confirmation=True；confirmed/cancelled → False）、`last_worker_summary`（最后 3 条工具结果摘要 ≤180 字）。

### 4.3 情绪（mood）的三套来源与忽略规则

1. supervisor 路由时产出（多 Agent 主路径，`_mood_resolved_by_supervisor=True`），发一条 `mood_update` UI 事件；
2. decision 轮模型调 `update_npc_mood` 工具 → 存 `_mood_tool_calls`（多 Agent 下 decision tools 不含它，理论上不会出现；legacy 路径依赖它）；
3. 生成轮 `generate_response_stream` 中若模型又调了 mood 工具，多 Agent 模式下该事件**被忽略**（`_mood_event_emitted` 检查）。

生成轮 tool suffix 会把 supervisor 已决定的 emotion/favorability 回显给模型要求「保持一致」。

### 4.4 生成轮工具策略

`_get_mood_only_tools`：多 Agent 模式返回 `[]`（生成轮完全无工具）；legacy/降级模式返回 mood 类工具。决策轮文本（`_decision_reply`）不参与最终回复，避免「决策轮自述」污染。

### 4.5 序列化与 SSE 事件体系

- `_ui_events` 列表随 state 累积（tool_status / agent_status / mood_update），流式路径用 `emitted_idx` 增量吐出；
- 系统消息 `{任务草案拟定完成}` 等以**花括号文本**拼进 `_system_prefix_text`，作为 content 一并流式推给前端（前端按 `{...}` 约定解析为系统消息，无独立 SSE 事件类型——注释解释：避免刷新后丢失、避免双渲染）；
- `build_in_turn_history_appendix` 把「本轮已推送给玩家的可见正文」（interim + 已发送的 `{...}` 系统消息）拼回 user prompt 末尾，让模型与玩家所见同步；
- `interim_reply_emitted`、`_streamed_prefix_for_llm`、`prefix_yielded_len`、`has_visible_content`、`reply_fragments` 等多组簿记变量在流式编排函数内维护。

### 4.6 死代码/未接线的多 Agent 相关物

- `services/agent_graph/graph.py`（单 Agent 三阶段图 + decision-loop 子图 + `get_full_graph`/`get_decision_loop`）：**全仓库无任何引用**。
- `SupervisorState.confirmation_payload`：声明、初始化为 None 后从未使用（HITL 实际靠「把确认消息合成一条 NPCChatRequest 重跑 ask_stream」实现，见 `/ask/confirm`）。
- `check_idempotent`（Redis SETNX 幂等）：定义后未挂到任何路由。
- `services/session_heartbeat.py` 整个模块（SSE 心跳续期）：无任何调用点。
- `README` 所称 `interrupt_before` HITL v1 已被弃用，当前为「HTTP 轮次天然 pause/resume」（thread_id + checkpointer 恢复 state）。

## 5. RAG 检索实现

### 5.1 索引构建（ai_engine/game_data_loader.py）

- 嵌入模型：`BAAI/bge-small-zh-v1.5`（**512 维**，24M 参数，本地目录 92MB；README/代码多处误写 384 维，见问题清单 C7），经 `HuggingFaceEmbedding`（**torch/transformers 栈**），强制离线环境变量，device=cpu。
- 文档源 6 类 → LlamaIndex `Document`（带 metadata.type / character 等）：
  1. `dialogues/*.xml` 日常对话（每 `<Dialogue>` 一条，character 小写）
  2. `task/*tasks*.json + text/*.json` 任务台词（单条 NPC 台词一 Document；guide 类打 `task_source=guide`）
  3. `docs/*.pdf/docx` 世界观（核心/补充两类；自定义按标题/段落/句子切分，256/512 token 规则）
  4. `stages/loading_data.xml` loading 短句
  5. `intelligence/*.txt` 情报（@@@X_Y@@@ 分节）
  6. `game_item / game_stage` 结构化实体（整实体一条，供任务实体提示）
- 持久化：LlamaIndex StorageContext 到 `resources/tools/vector_index`；启动时后台任务链「加载模型 → 加载/构建索引」，首个请求前 `ensure_embed_model_ready()` 阻塞等待。

### 5.2 生产检索路径 `_retrieve_context`（game_rag_service.py，约 500 行同步函数）

**8+ 个 dense retriever，全部串行执行**（每次调用都是一次 embedding + 向量检索）：

| retriever | top_k | query 来源 | 阈值 |
|---|---|---|---|
| npc_retriever（本 NPC 日常台词） | 8 | user_query | 无 |
| world_lore_retriever | 3 | retrieve_query(用户+NPC名+称号+阵营) | 0.22 / NPC 查 0.28 |
| loading_lore_retriever | 7 | retrieve_query | 0.28 / 0.32 |
| task_retriever（本 NPC 任务台词） | 10 | user_query + npc_last_message | 0.28 / guide 0.38 |
| supp_retriever + intel_retriever（合并池） | 3+3 | retrieve_query | 0.30 / 0.36 |
| other_dialogue/task_retriever（其他 NPC） | 15+15 | user_query+NPC名 / npc_last_message | 0.36~0.48 |
| （另有 game_item / game_stage 实体检索 top4，阈值 0.48） | | | |

- 若有 NPC 上一条发言，几乎所有池子都要**再跑一轮检索**并按更高阈值少量合并 → 实际单轮检索执行 12~16 次。
- 「其他 NPC 对话参考」有复杂名额策略：先保 2 条非引导任务，再 3 条自由竞争；NPC 上一条再补 ≤2 条；排序 key = (任务优先, 是否提到当前NPC, 分数)。
- 彩蛋/成员阵营台词不排除而是**附加「非正式角色」标注**并提高阈值。
- 输出按 6 类拼 section（每类有不同 max_chars：350/300/不截断等），行级去重、空行压缩。
- 附加 `_build_game_data_context_hints`：全量物品/关卡的**子串匹配**（`name in query`，按名字长度倒序遍历全部条目，命中≤10）+ 向量实体补充，拼「玩家可能提到的物品类型/关卡」提示。

### 5.3 BM25 / Hybrid（ai_engine/bm25_retrieval.py）

- 实现完整（rank_bm25 + RRF 融合 + pickle/内存缓存，fingerprint=节点数+前50个id）。
- **生产路径完全没有调用它**——`_retrieve_context` 只有 dense；BM25/hybrid 仅用于 `evals/` 与 `retrieve_nodes_for_eval`。README 宣传的「多路 Dense + BM25 + Hybrid RRF 检索」在生产链路上不成立（_dense 单路多池_）。
- BM25 的 `filter_nodes_by_metadata` 每次检索都全量线性扫描 docstore 节点。

### 5.4 向量后端抽象（services/storage/）

- `VectorBackend` Protocol + `LlamaIndexLocalBackend`（to_thread 包装）+ `QdrantBackend`（384 维 Cosine，payload 过滤转换）。
- server profile 下 `game_api.py` 会构造 `QdrantBackend` 并注入 `GameRAGService(vector_backend=...)`，**但 `_retrieve_context` / `_collect_vector_game_entity_extras` 全部直接用 `self._get_index()`（本地 LlamaIndex），从不读 `self._vector_backend`**。
- worker 的 `rebuild_vector_index` 任务注释说「若配置了 Qdrant，同步迁移向量数据」，实际函数里**没有任何 Qdrant 写入代码**；Qdrant 数据只能靠手动脚本 `scripts/migrate_vector_to_qdrant.py` 迁移。
- 即：server profile 的 Qdrant 检索**没有任何读路径与写路径**，只有注入的死参数。

### 5.5 相似度阈值体系

检索里散布大量手调阈值常量（0.22/0.28/0.30/0.32/0.36/0.38/0.40/0.44/0.48），每个池子两档（用户查/NPC上一条查），guide/彩蛋再上浮。

## 6. Prompt 体系（services/agent_graph/prompts.py）

分层设计（2026.04 修订版）：

- **system（static，L1+L2+tagline）**：固定世界观 WORLD_BACKGROUND（硬编码在 game_rag_service.py 内）+ NPC 扮演约束 + 商店奖励类型约束 + 切磋约束 + 同阵营角色表。全部 agent 共用（supervisor 也要 NPC 口吻出 interim 和 mood）。
- **user（shared core）**：RAG 块 → 提及 NPC 块 → 会话状态（玩家身份/进度/好感/待确认草案摘要）→ 对话历史。同一轮多 agent 共享，实现前缀缓存命中（README 实测 85-95%+）。
- **per-agent tail（user 侧）**：supervisor 路由规则/JSON schema、query/task 工具纲领+Skills 索引白名单、dialogue 输出格式规则（【】动作格式、第三人称、禁半角括号等）。
- 决策轮/生成轮各有 suffix 常量；「已推送正文」appendix 机制（§4.5）。
- Skills 渐进披露：`services/skills/*/SKILL.md`（YAML frontmatter + body + references/），Level1 简表（白名单过滤）→ Level2 read_skill → Level3 read_skill_file。
- 兼容层较多：`build_prompt_base` / `build_system_prompt` / `build_user_prompt` / `TOOL_USAGE_GUIDE`（空壳）等旧入口保留，多个参数用 `_ = (...)` 显式忽略。

## 7. 任务发布管线（tools → agent_tools 纯函数）

### 7.1 工具层（services/tools/）

每个工具一个文件（BaseTool 子类，硬编码 JSON schema，`ToolRegistry.discover` 扫描 `services/tools/{category}/*.py` 注册；`dispatch` 同步执行）。工具间通过 `ToolContext`（npc 信息、pending_draft、retrieve_fn、rag_context_text、game_data 等）取数。

### 7.2 两步式 + HITL

1. `prepare_task_context(task_type, reward_types, keywords…)` → `context_builder.prepare_task_context`（**2364 行**手调筛选：关卡/物品/奖励/挑战目标候选 + 配额分配「82/55/532」+ 关键词置顶 + 随机打散）。
2. `draft_agent_task(...)` → 全量校验（V1-V11）→ 存草案（draft_id=uuid[:8]）→ 返回 draft_summary；**draft/updated 状态触发 task worker 硬退出**，等待玩家。
3. `update_task_draft(draft_id, modify_fields)`：仅变更字段；奖励类变更且原草案有效 → 计讨价还价次数（上限 2 次，超限报错），bargain_rate=1.5 只放大 V7 上限；增量校验（changed_fields 决定跑哪些 V 规则）。
4. `confirm_agent_task(draft_id, title, description, get_dialogue[], finish_dialogue[])`：draft_id 必须匹配 pending；合并后**再次全量校验**；通过则 `write_confirmed_agent_task_files`（threading.Lock + 临时文件 + os.replace 原子写两个 JSON；ID 在锁内扫磁盘文件取 max+1，200001-300000 段；标题自动去重加罗马数字后缀；对话条目剥【】动作、映射 `$PC_CHAR#情绪`；get_requirements 由关卡 unlock_condition 反推并 clamp ≤77；bump task_publish_version）。
5. `cancel_agent_task`。

### 7.3 校验管线 V1-V11（services/agent_tools/validator.py）

| 规则 | 内容 | 失败返回信息 |
|---|---|---|
| V1 | 物品存在性 | missing_item_names + 「重新调用 prepare_task_context」提示 |
| V2 | 数量合理性（历史统计 ×2 / 无统计时按价格估算） | quantity_issues + allowed_range |
| V3/V3R/V4/V5 | 关卡存在、副本推荐等级、解锁进度、难度 | invalid_stages / over_progress_stages（无替代建议） |
| V6 | 前置任务 ID 合法（禁 -1） | invalid_precondition_ids |
| V7 | 奖励总价值区间（stage 基数×战斗×2、提交/持有加成封顶、好感系数 0.9-1.2、bargain_rate≤1.5） | item_prices + total_value + allowed_range + 文字建议 |
| V8 | 奖励类型合规（历史奖励类型 ∪ NPC 商店） | non_compliant_items |
| V9 | 任务高度雷同（结构指纹完全一致）→ **仅 warning** | similar_task_ids |
| V10 | 装备等级 ≤ 阶段上限 | over_level_items |
| V11 | submit 与 rewards 不得重名 | duplicate_item_names |

- `validate_task_draft` **串行短路：命中第一条错误立即返回**，一次只给模型一个错误。
- 无任何「后端小幅自动修正」逻辑（数量/价值差额全部打回模型）。
- 重试控制仅靠 LangGraph 工具轮上限（task worker 4 轮）+ supervisor hop 限制；无针对校验失败的专门重试预算或终止策略。

## 8. 存储层

- **MemoryManager（SQLite）**：每次操作新建 sqlite3 连接（`asyncio.to_thread` 包裹）；三张表 chat_history / sessions / session_summaries；摘要按条数间隔触发（fire-and-forget `asyncio.create_task`，用**当时的 llm_config**——即用户/前端传入的 key 生成摘要）。
- **SqliteBackend / PostgresBackend**（services/storage/db.py / postgres_db.py）：SessionStore/MessageStore/DraftStore 协议；SqliteBackend 是 MemoryManager+SessionTaskDraftStore 的适配器（`save_summary` 直接调私有方法 `_save_summary`）。
- **SessionTaskDraftStore**：session_task_drafts 表（session 唯一草案）+ ask 计数器表；草案自动过期：连续 3 次 ask 未碰任务工具即删除。
- **NPCManager**：全量 JSON 文件读写（每请求 load、每次 save 全量写）；无锁、无进程内共享。
- **CacheBackend**：MemoryCache / RedisCache；Redis 在生产代码中的实际使用点：无（幂等未接线、心跳未接线、会话热缓存未接线）——`get_server_cache` 也只在 check_idempotent 中被引用。
- **写入游戏文件**：`agent_tasks.json` / `agent_text.json` 原子写（threading.Lock 进程内）；启动时 ensure 文件存在并在 list.xml 中注册条目。

## 9. 启动与性能相关事实

- `core/startup.py`：启动任务全后台化——ensure 任务文件、NPC 状态库（优先从打包内 backup 复制，否则跑脚本生成）、illustration.zip 解压、嵌入模型预载（`get_text_embedding("")` 预热）→ 索引加载/构建（`get_cached_index`，存在则加载，不存在则构建 10-30s 并持久化）、GameDataRegistry 加载。
- 首个对话请求 `await ensure_embed_model_ready()` 同步等待模型就绪。
- 首字延迟分步追踪：`LatencyTracker`（仅 CFN_AGENT_DEBUG_LATENCY 打开时输出 stderr，平时近乎零开销）。另有一个「真实首字延迟测量」相关待办不在代码中。
- `main.py`：uvicorn 直跑 127.0.0.1:7077，`reload=True` 硬编码在 `__main__`；CORS allow_origins=["*"]。
- `launcher.py`（1063 行）：Python 环境检查、单实例互斥、tkinter 状态窗/加载音效、起后端子进程、`http.server.SimpleHTTPRequestHandler` 手写前端静态服务 + `_proxy_to_backend`（含 SSE 转发）。
- 打包：`scripts/build_exe.py`（PyInstaller 单文件）打包 dist/models/scripts/tools/backup_resources 等；嵌入链路带入 **torch 2.10 + transformers 5.3**（requirements 全量同装：ragas/datasets/locust/alembic/qdrant/arq/fastmcp/prometheus 等一并进入打包池）。
- 代理：`apply_proxy_config` 直接改 `os.environ["HTTP_PROXY"/"HTTPS_PROXY"]`（进程级全局，随任一请求的 payload 变化）。
- LLM 客户端无连接池复用、无超时/重试/退避；图像每次请求重新 PIL 处理 + base64。
