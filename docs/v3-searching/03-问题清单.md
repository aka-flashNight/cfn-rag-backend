> 本文只列**明确有问题**的地方与**疑似问题/待验证点**，不给修正方案与技术方向。
> 每条注明代码位置与判定依据（明确问题均有代码证据；疑似问题只描述疑点本身）。
> 「模型能力运用」一节的判定结合了 `02-联网调研-模型与工具调用.md` 的业界现状佐证。

## 一、明确问题

### A. 模型调用与协议层

**A1. 「不支持工具」的判定过宽：任何 400/422 都会被当作模型不支持工具**

- 位置：`services/npc_mood_agent.py:72-85`（`is_tools_unsupported_error`：`status_code in (400, 422)` 直接返回 True）
- 后果：模型名写错、上下文超长、参数非法、配额类 400 等所有 Bad Request 都会触发「去掉工具重试」的静默降级，浪费调用且掩盖真实错误；重试大概率再次失败，最坏情况沿 2×2 回退矩阵连续发起 4 次 LLM 调用（见 A2）。

**A2. 「图/工具」组合回退矩阵在 5 处复制粘贴**

- 位置：`game_rag_service.py`（`_ask_legacy` ~600-669、`_ask_stream_legacy` ~1023-1048）、`agent_graph/nodes.py`（`decision_node` ~826-842、`generate_response_node` ~1081-1139、`generate_response_stream` ~1283-1318）
- 每处都是「带图+工具 → 无图+工具 → 带图无工具 → 无图无工具」的手写嵌套重试。行为细节还互不一致（流式版多了「已输出正文就不再重试」的防重逻辑），是典型的高漂移风险复制代码。该兼容手段针对的历史问题（Gemini OpenAI 兼容层流式+tools 不共存）按联网调研（`02-联网调研-模型与工具调用.md` §1/§3.1）**在现行各家 API 中已不复存在**，当前主流模型流式+工具调用+视觉可同时开启。

**A3. 通用 LLM 客户端层硬编码业务工具 `update_npc_mood` 并在流式中途解析部分 JSON**

- 位置：`services/llm_client.py:178-258`（`_emit_mood_updates`：每收到 tool_call delta 就尝试 `json.loads` 参数串，可解析即发 `mood_update`）
- 基础设施层耦合具体业务工具名与参数结构；该「参数前缀可解析即推送」机制对参数书写顺序敏感（必须先凑齐 `emotion`+`favorability_change` 两键），是精细但脆弱的字符串级解析。

**A4. 流式正文的字符串截断规则会吞掉合法内容**

- 位置：`game_rag_service.py:972-1016`（`_TRUNCATE_PREFIXES = ["工具调用", "{", "<!---", "<!--", "update_npc_mood(", "tool_calls_list"]`，出现即从该处截断正文）
- 后果：NPC 回复里只要出现 `{`（或被判定为工具调用样式的文字），从该字符起到结尾的全部正文被丢弃。末尾 JSON 防御与正文截断混在一条规则里，无法区分「模型把工具参数写进正文」与「台词本身含花括号」。
- 同类：`npc_mood_agent.py:99-147`（`strip_trailing_tool_call_text`）按段落中出现 `emotion`/`favorability_change`/`{...}` 关键词即删除该段及之后所有内容——台词讨论到"情绪""好感度"等词同样命中。

**A5. 每次调用新建客户端；主路径无超时/重试/退避**

- 位置：`services/llm_client.py:49,183`（每次 `AsyncOpenAI(...)`）；`call_llm`/`call_llm_stream` 未设置 timeout、重试、连接复用（仅 evals 路径有 900s 超时）。

**A6. 除 tools 外不控制任何调用参数；无 usage 统计**

- 无 `response_format`（结构化输出）、`tool_choice`、`parallel_tool_calls`、`temperature`、`max_tokens`；无 token 用量回收。
- 后果①：supervisor 的路由 JSON 只靠 prompt 约束 + 正则兜底（`supervisor.py:105-152`），docstring 声称「尝试 response_format=json_object」但代码并未使用。
- 后果②：`token_budget_spent` 初始化为 0 后**没有任何节点累加它**（全仓库仅 `prepare_context_node` 置 0、`supervisor._hard_guard` 读值），40k token 熔断器永远不会触发。
- 联网佐证：见 `02-联网调研-模型与工具调用.md` §3.2/§3.3（各家已普遍支持 strict/structured output 与并行工具调用，现行协议能力远未被使用）。

**A7. 对推理型模型的输出形态无处理（疑似升格为明确的风险点）**

- `call_llm*` 均未处理 `reasoning_content`/思考字段或 `<think>` 类标签；若切换到思考型模型（用户候选模型均为思考/混合推理型），思考内容可能直接混入正文与流式输出。联网调研（`02-联网调研-模型与工具调用.md` §3.4）显示候选模型默认可能输出思考内容且有对应协议字段与回传规则，现实现完全未涉及。→ 列入明确「能力缺口」。

### B. 多 Agent 编排

**B1. 流式路径完全绕过 LangGraph，手动重写了一遍编排**

- 位置：`game_rag_service.py:744-958`（`_ask_stream_with_graph`）vs `services/agents/graph.py`
- 非流式走编译图，流式手动顺序调节点并自维护事件簿记（`emitted_idx`/`prefix_yielded_len`/`has_visible_content`/`reply_fragments`/`_streamed_prefix_for_llm` 等）。两条路径各自维护 mood 处理、系统前缀、final_reply 拼装的逻辑，已经出现细节分叉（如流式路径以「已推流内容」为准、非流式以节点拼装为准）。

**B2. 全链路零并行，多 Agent 形态实为串行流水线**

- 拓扑：supervisor →（单选 1 个 worker）→ dialogue → finalize（`agents/graph.py:114-116` 静态边）；worker 内部 decision↔tool_executor 串行循环；`tool_executor_node` 用同步 `for` 逐个执行同批 tool_calls（`nodes.py:921-999`）。
- 一条消息固定 2~3 次串行 LLM 调用（supervisor + worker 决策×N + dialogue），任何阶段都无法与其他阶段并行。与「多 Agent 并行派发」的业界形态（`02-联网调研-Agent编排.md` §2/§3）差距明显。

**B3. 同批工具执行同步阻塞事件循环**

- 位置：`services/tools/base.py:176-204`（`dispatch` 同步）、`nodes.py:960-964`（在 async 节点内直接调用，未 `to_thread`）
- 后果：`search_knowledge` 工具会同步触发 `_retrieve_context`（单次 12~16 次嵌入+向量检索，见 C1），期间整个 FastAPI 事件循环被阻塞，**所有并发用户的请求全部停摆**。RAG 初始化检索走了 `asyncio.to_thread`，而工具内检索没有。

**B4. 「四重防护」在当前拓扑下全部失效（死逻辑）**

- 位置：`agents/supervisor.py:42-49`（MAX_HOPS=6、MAX_PER_WORKER_CALLS=3、连续失败≥2 拉黑、TOKEN_BUDGET_HARD_CAP=40k）
- 逐一验证：
  - `worker_hops`、`agent_call_counts`、`agent_consecutive_failures`、`agent_blacklist` 在 `prepare_context_node` 中**每请求重置**（`nodes.py:717-720`）；
  - 当前拓扑 supervisor 每请求只跑一次、每个 worker 至多跑一次 → hops 恒为 1（<6），per-worker 计数恒为 1（<3）；
  - blacklist 在 supervisor 路由**之前**永远是空的（失败计数发生在 worker exit，之后不再有 supervisor）；
  - `token_budget_spent` 从不累加（见 A6）。
- 即 README 宣传的「per-agent 上限 / 连续失败黑名单 / token 熔断 / 全局 6 轮出口」四个防护机制实际一个都不会触发。

**B5. supervisor 的情绪决定发生在对话生成之前**

（经开发者确认，这不是问题，在对话前必须先将情绪返回给前端，前端切换立绘，然后再输出对话内容。否则会出现说完话才变化表情的问题。）

- 位置：`supervisor.py:440-468`；生成轮不提供任何工具、回显「已决定的情绪」要求保持一致（`nodes.py:201-232`、`prompts.py:327-335`）
- 设计事实：情绪由「路由判断」阶段的模型一次性敲定，dialogue 生成模型无权再调 `update_npc_mood`（多 Agent 模式下生成轮 tool list 为空，`nodes.py:157-165`）。情绪与正文的一致性只靠 prompt 回显约束。

**B6. 一批未接线的多 Agent/基础设施死代码**

- `services/agent_graph/graph.py` 整文件（单 Agent 图 + decision-loop 子图 + 全局单例）：无任何引用；
- `SupervisorState.confirmation_payload`（HITL v2 遗留）：仅声明与置 None；
- `interim_reply_emitted`：仅写入从未读取；
- `api/game_api.py:138` `check_idempotent`（Redis SETNX 幂等）：未挂任何路由；
- `services/session_heartbeat.py` 整个模块（SSE Redis 心跳）：无调用点；
- `latency_sleep_zero`、`prompts.py` 的 `TOOL_USAGE_GUIDE`（空壳）等兼容残留；
- `_emit_handoff_status`/`agent_status` 事件：前端不显示（代码注释自述），仍每跳生成。

### C. RAG 检索

**C1. 单轮对话最多执行 12~16 次串行「嵌入+向量检索」，且同一 query 被重复嵌入多次**

- 位置：`game_rag_service.py:1266-1757`（`_retrieve_context`）
- 8+ 个 retriever 全串行；有 NPC 上一条发言时几乎所有池子再查一轮。LlamaIndex 每次 `retrieve()` 都会对 query 重新做一次嵌入：`retrieve_query`（用户输入+NPC名+称号+阵营）被 world_lore/loading/supp/intel 等池子重复嵌入约 5 次，`user_query` 被 npc/task/other 等池子重复嵌入约 4 次，均为重复计算。

**C2. 生产检索没有 BM25/Hybrid，与 README 描述不符**

- `ai_engine/bm25_retrieval.py` 实现完整，但生产链路只有 dense；BM25/RRF 仅在 `evals/` 与 `retrieve_nodes_for_eval` 中使用。README「多路 Dense + BM25 + Hybrid RRF 检索」指的是评估体系而非生产路径。

**C3. Qdrant 后端只有「注入」没有「读写」，server profile 向量检索名存实亡**

- `api/game_api.py:78-81` 注入 `QdrantBackend`；但 `GameRAGService._retrieve_context`、`_collect_vector_game_entity_extras` 一律走 `self._get_index()`（本地 LlamaIndex），`self._vector_backend` 从未被读取；
- `worker/tasks.py:32-67` 的重建任务注释称「若配置了 Qdrant，同步迁移向量数据」，函数体内没有任何 Qdrant 写入；Qdrant 数据只能手动跑 `scripts/migrate_vector_to_qdrant.py`。
- 后果：server profile 下检索仍依赖本地构建/加载 `vector_index`，Qdrant 成为纯摆设；`qdrant_vector.py:179` 的 `payload.pop("_node_content", payload.pop("text", ""))` 写法也有求值顺序疑点（见二类疑似）。

**C4. 检索体系为大量硬编码魔数**

- 相似度阈值 0.22/0.28/0.30/0.32/0.36/0.38/0.40/0.44/0.48（各池两档）；「其他 NPC」名额策略（2+3、1+1）；排序 key 元组；各类 section 的 max_chars（300/350/不截断）；`context_builder.py` 2364 行中的配额模式 "82"/"55"/"532" 等。全部散落在函数体内，无配置、无评估联动。

**C5. `_retrieve_context` 单函数约 500 行，同步、混合了检索/过滤/去重/拼装/实体提示五类职责**

- 仅通过 `retrieve_nodes_for_eval`（单池模式）可供评估复用，生产路径本身无单元测试切口。

**C6. 关键词命中为全量子串匹配**

- `game_rag_service.py:1853-1936`：按名字长度倒序遍历**全部**物品与关卡做 `name in query` 子串匹配（每次对话 2 遍：user_query + NPC 上一条）。

**C7. 嵌入向量维度在代码与文档中写错（384 ≠ 实际 512）**

- 实测：`models/bge-small-zh-v1.5/config.json` → `"hidden_size": 512`；官方规格亦为 512 维（384 是英文版 bge-small-en-v1.5 的维度）。
- 写错的位置：`services/storage/qdrant_vector.py:20`（`EMBEDDING_DIM = 384`，注释即写「bge-small-zh-v1.5 输出维度」）、`scripts/migrate_vector_to_qdrant.py:76`（按 384 建 collection）、README 三处（384 维）。
- 影响：Qdrant 路径若真被启用，按 384 维建 collection 后插入 512 维向量将维度不匹配；因该路径当前是死代码（C3），故为「潜伏错误」而非现行故障。核实来源：`02-联网调研-向量模型.md` §0。

**C8. BM25 过滤每次全量线性扫描**

- `ai_engine/bm25_retrieval.py:31-53`：`filter_nodes_by_metadata` 对 docstore 全部节点逐个字典比对；`bm25_retrieve` 每次调用都先 `iter_docstore_nodes` 全量拉节点。当前仅 evals 使用，若进入生产语料增大后是明确瓶颈点。

### D. 校验打回（任务管线）

**D1. 校验串行短路：一次只返回一个错误**

- 位置：`validator.py:871-995`（每条规则 `if e: return`）
- 草案若有 3 处不合规，模型需要 3 轮「决策 LLM 调用 + 工具执行」才能全部修完；每轮都是真实延迟与 token 成本。

**D2. 没有任何后端小幅自动修正；差额无论多小一律打回**

- V7 价值差 1 金币、V2 数量超 1 个、V10 超级 1 级等，全部生成 `validation_failed` 重新走模型修正；后端明知合法区间与单价明细，却不代为调整或给出「差额数值」的明确指示（V7 错误文案带区间与总价，但不含「需增/减多少」的直给数值）。

**D3. 多数错误信息缺少「下一步怎么做」的定位信息**

- 对比：V1/V3 的文案明确说「重新调用 prepare_task_context 查看候选」（较完整）；V4 只给 `min_unlock_id`/`main_task_max_id`，不告诉模型哪些关卡可用；V8 给 reason 但不给「当前 NPC 商店/历史奖励的可选类型清单」；V2 给 allowed_range 但不给候选物品。打回后模型主要靠自己的记忆或再调一次 prepare 来猜。

**D4. 校验失败时 `draft_summary` 返回空字符串**

- `handlers.py:152-159,252-257`：`validation_failed` 响应中 `draft_summary: ""`。同一 worker 轮内模型还能从历史 tool_messages 看到上一次成功的 summary；一旦发生降级/跨轮，修复上下文依赖 pending_draft 摘要块，信息链路变窄。

**D5. 讨价还价计数与 `_draft_commit_valid` 内部标志混入业务草案数据**

- `bargain_count`、`_draft_commit_valid`（下划线内部字段）直接存进 draft dict 并随草案持久化入库（`task_draft_store` 全量 JSON 存储）；跨层耦合的数据形态。

### E. 存储与并发

**E1. NPC 状态并发读写无保护**

- `api/game_api.py:129-131`：每个请求 `NPCManager.load()` 全量读 JSON；对话后 `update_favorability` + `save()` 全量写 JSON；无任何锁。
- 后果：两个并发会话与同一 NPC 互动时，好感度更新互相覆盖（last-write-wins）；读-改-写窗口内的所有变更丢失。

**E2. 摘要生成 fire-and-forget，无生命周期管理**

- `memory_manager.py:216-218`：`asyncio.create_task(_safe_summarize(...))` 无并发上限、无超时、进程退出即丢、失败仅日志；摘要 LLM 调用使用**用户请求当时传入的 api_key/model**，意味着前端传了免费 key，摘要用同一个 key（用户未必知情）。

**E3. 代理配置修改进程级全局环境变量**

- `api/game_api.py:43-62`：任一请求携带 `proxy_url` 即改写 `os.environ["HTTP_PROXY"/"HTTPS_PROXY"]`，影响**所有**后续请求的 openai/httpx 客户端。多会话下互相覆盖（A 用户清代理会立刻切断 B 用户的代理）。

**E4. SQLite 每操作新建连接；双数据形状并存**

- `memory_manager.py` 每个 CRUD 新开 `sqlite3.connect`（靠 to_thread 避免阻塞，但无连接池/复用）；
- `MemoryManager.get_history` 返回 dict 列表，`SqliteBackend.get_history` 返回 `ChatMessage` dataclass；API 依赖注入类型标注写的是 `MemoryManager`，实际传入的是 `SqliteBackend`/`PostgresBackend`——两套接口形状并存，类型标注失真。

**E5. Redis 在 server profile 的实际使用为零**

- 唯二引用（幂等、心跳）都是死代码（见 B6）；`get_server_cache` 仅被死代码调用。README 宣传的「RedisCache（热会话缓存/心跳/幂等）」未真正落地。

### F. 启动、性能与打包

**F1. 单 exe 体积 357MB 的主因是 torch/transformers 栈，而非模型本身**

- 实测：`CFN-RAG-v2.9.9.exe` 357MB；`models/bge-small-zh-v1.5` 仅 92MB；venv 1.5GB。
- 嵌入链路 `llama-index-embeddings-huggingface` → `transformers 5.3.0` + `torch 2.10.0`（pip 实测在装）。
- requirements.txt 未分组：`ragas/datasets/locust/alembic/qdrant-client/arq/fastmcp/prometheus` 等评估/服务端/压测/MCP 依赖与本地运行依赖混装，全部进入打包候选。

**F2. 首次索引构建 10~30 秒（README 自述）+ query 重复嵌入（C1）+ 立绘每请求重复处理**

- `portrait_utils.prepare_portrait_for_ai` 每次请求对同一立绘重新 PIL 裁剪+缩放+WebP 编码+base64，无缓存。

**F3. `main.py` 的 `__main__` 入口硬编码 `reload=True`**

- `main.py:149`。launcher 路径用的是 `reload=False`（`launcher.py:580`），风险限于开发习惯，但两处不一致。

**F4. 日志以 print 为主**

- `ai_engine/game_data_loader.py` 35 处、`core/startup.py` 37 处 print；结构化日志仅 server profile 生效。

### G. 文档与实现不符（README）

1. 「DialogueAgent 携带 update_npc_mood 单一工具 + stream=True」——多 Agent 模式下生成轮**不传任何工具**（`nodes.py:_get_mood_only_tools`），mood 由 supervisor 决定。
2. 「防护机制四件套」——全部失效（见 B4）。
3. 「多路 Dense + BM25 + Hybrid RRF 检索」——生产仅 dense 多池（见 C2）。
4. 「Skills：mood-tracking」——`services/skills/` 下不存在该目录（仅 knowledge-search / skill-discovery / task-bargaining / task-publishing）。
5. 「Qdrant 向量数据库（server profile）」「RedisCache 热会话缓存」——均未实际接线（C3/E5）。
6. interim_reply 长度：README 写 ≤40 字，代码为 ≤80 字（`supervisor.py:134-135`）。
7. README 架构图宣称 supervisor 可多轮回环路由，实际为单跳路由（supervisor 判一次，worker 后静态进 dialogue）。

## 二、疑似问题（不下结论，列出疑点）

**S1. `_hit_to_node` 的 `payload.pop` 嵌套写法**

- `qdrant_vector.py:179`：`payload.pop("_node_content", payload.pop("text", ""))`——Python 先求值默认参数，`text` 键先被 pop 掉；若 payload 同时含 `_node_content`（LlamaIndex 序列化的 JSON 字符串）与 `text`，取到的将是 `_node_content` 的原始 JSON 而非正文。需对照 `migrate_vector_to_qdrant.py` 的写入格式才能判定是否实际踩坑。

**S2. 工具同步执行是否「必然」卡顿取决于检索耗时**

- B3 的实际影响幅度未实测（本地索引小时检索可能只有几十毫秒）；但 `search_knowledge` 路径包含 12~16 次检索（C1），叠加后单次工具执行可能在数百毫秒~秒级，事件循环阻塞期间所有 SSE 心跳/其他用户流全部停住。

**S3. supervisor 规则短路的正则覆盖面**

- `_rule_route_pending_draft`（`supervisor.py:200-255`）用固定中文短语/正则匹配「接受/拒绝/议价」。列表之外的口语（如「成交价再谈谈」「这任务我收下了」）会落到 LLM 路由——是否有漏判导致误路由，未验证。

**S4. 流式路径 final_reply 与入库文本的一致性兜底**

- `_ask_stream_with_graph` 以 `reply_fragments` 为准，但当 `emitted_reply` 为空时回退为「interim + prefix + dialogue_body」三段拼接（`game_rag_service.py:920-927`）；异常中断（如 SSE 断连）时 post_process 是否执行、done 事件与库内文本是否一致，无测试覆盖。

**S5. update_task_draft 的增量校验盲区**

- `validator.py:859-869`：增量模式只跑「被改字段」关联的规则。改 `finish_submit_items` 会触发 V7（submit 参与预算公式），但改 `finish_requirements` 不触发 V10/V2（合理）；反向场景——某字段的历史状态在旧草案中已失效（如玩家进度在草案存续期间变化），增量校验不会发现。触发条件苛刻，未验证。

**S6. 摘要与历史的「间隔」语义**

- 摘要在消息数达到 interval 整数倍时触发，且摘要对象是「最近 interval 条」而非「自上次摘要以来的新增」；`_summarize_history` 用旧摘要+最近 30 条滚动整合。长会话下信息保真度是否够，无验证手段。

**S7. legacy 路径的图像/工具回退与 agent 路径行为差异**

- `progress_stage` 缺失或 agent_enabled=false 时静默走 legacy：无任务能力、prompt 结构不同（`_prepare_ask_context` 另一套 system/user 拼装）。同一前端在不同请求参数下会得到两套不同对话质量/能力，是否为预期产品行为待确认。

**S8. `is_image_unsupported_error` 的关键词判定**

- 按 `image`/`vision`/`expected...text` 等英文关键词匹配；各家报错文案一变即失效（与 A1 同根：错误分类靠字符串嗅探而非错误码结构）。

**S9. 前端传 key/base_url/model 的安全与一致性**

- `NPCChatRequest` 接受前端直传 api_key/api_base/model_name，并按消息存入 llm_config；本地单用户产品形态下是否可接受待定，但 server profile 下这是把密钥经手存库的设计。

**S10. CORS `allow_origins=["*"]` 与 `allow_credentials=True` 并用**

- `main.py:124-130`：按 CORS 规范该组合无效（浏览器拒绝带凭证的通配源）；当前前端走 launcher 同源反代，实际影响面小，但属于配置隐患。

**S11. `_simulated_content_chunks` 的固定 sleep（6 字/30ms）**

- 伪流式节奏与人正常阅读速度的匹配未验证；interim 最长 80 字意味着额外 ~400ms 人为延迟。

**S12. evaluate 体系与生产参数脱节**

- evals 评的是「单池 dense/bm25/hybrid」与 golden 集，而生产是「多池多阈值拼装」；检索配置调参（C4 的魔数）没有对应的评估回路。

**S13. `chat_history` 无软删除/会话隔离约束**

- 消息表仅 session_id+timestamp；`delete_session` 物理删除；无 user/device 维度。单机形态够用，server 形态下多用户隔离缺失（与 S9 同域）。

**S14. `find_resources_directory` 的路径探测顺序**

- `memory_manager.get_db_path` 有 3 级回退（exe 目录 / cwd / 父目录）；打包与环境变量混用时数据库/索引落点是否稳定，未验证。

## 三、模型能力运用层面的差距（结合联网调研佐证）

> 详细证据见 `02-联网调研-模型与工具调用.md`。此处仅列「当前实现 vs 现行模型能力」的落差点。

1. **流式 + 工具 + 视觉同时开启**已是主流模型的常规能力，当前代码仍按「互斥回退矩阵」设计（A1/A2）。
2. **结构化输出 / strict function calling** 已普遍可用，当前所有 JSON 输出（supervisor 路由、草案）依赖 prompt+正则（A6）。
3. **并行工具调用**（一次返回多个 tool calls 并行执行）未使用，当前同批工具按流水线排序后串行同步执行（B2/B3）。
4. **思考/推理型模型协议**（reasoning 字段、思考内容隔离）未处理，而候选模型（GLM-5.3-Flash、DeepSeek-V4-Flash-Vision-Exp 等）均属思考型（A7）。
5. **视觉输入**已用 OpenAI image_url 格式，这部分与现行协议一致（无明显问题）。
6. **prompt caching**：项目已做了前缀对齐设计（system 静态化、user 分层），但无 cache token 的量化回收与监控（无 usage 统计，A6），缓存收益不可观测。
