# 联网调研：2026 年 9 月主流模型与工具调用能力现状（v3 重构前置调研 · 二之一）

> 只报告事实，不含选型建议。信息以官方文档/官方公告优先，社区信息单独标注。
> 检索时间：2026-09-05；范围以近 3 个月（2026-06 至今）为主。

---

## 1. 结论速览

1. **「流式输出与工具调用不能共存」的问题在现行主流模型上已不存在**：GLM-5.3-Flash 官方文档直接列明同时支持流式输出与流式工具调用；DeepSeek、Qwen、OpenAI、Gemini 的现行 API 均为流式+tools+视觉同时开启的常规用法。2024~2025 年初 Gemini OpenAI 兼容层的该类缺陷未再见于近三个月的资料。
2. **候选模型全部为「思考型」模型**：GLM-5.3-Flash 思考模式恒开；Qwen3.8-Flash 开启思考后工具调用前会输出 `reasoning_content` 且多轮需回传；DeepSeek 系思考+工具调用为官方主推能力。处理 `reasoning_content` 字段是接入这些模型的前置条件。
3. **结构化输出（strict json_schema）**：Qwen、GLM、OpenAI 支持完整；DeepSeek 文本输出仅 `json_object`，严格 schema 只作用于工具参数（function.strict）；「function.strict 与 response_format.strict 是两个独立能力」是聚合平台的明确提醒。
4. **并行工具调用**：DeepSeek 强制开启（Responses 兼容端点忽略 `parallel_tool_calls` 参数）；OpenAI 官方 strict structured outputs 与并行函数调用存在已知互操作问题；各家均支持并行调用本身。

## 2. 用户候选模型逐个现状

### 2.1 GLM-5.3-Flash（智谱，2026-08-26 发布，MIT 开源）

- **规格**：320B 总参 / 18B 激活（MoE），稀疏注意力+线性注意力混合架构；1M 上下文，最大 128K 输出。
- **多模态**：GLM-5 系列首个**原生多模态**模型，原生图像/视频输入。
- **工具调用**：官方文档明确列出 Function Calling + **流式工具调用**（streaming tool calls）同时支持；支持上下文缓存、结构化输出。
- **思考模式**：官方描述为「思考模式始终开启」（官方文档原文）。
- **定位/价格**：官方主打「极致低成本」，媒体称价格约为 DeepSeek 的十分之一量级（知乎实测帖，社区信息）。
- 来源：[智谱官方文档 GLM-5.3-Flash](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash)（2026-08）、[智谱研究页](https://www.zhipuai.cn/zh/research/163)、[阿里云模型页](https://help.aliyun.com/zh/model-studio/glm-5-3-flash-by-zhipu)、[知乎实测（社区）](https://zhuanlan.zhihu.com/p/2076420786865304416)。

### 2.2 DeepSeek-V4-Flash-Vision-Exp（DeepSeek，2026-08-21 上线，实验性）

- **性质**：V4-Flash（2026-07-31 正式发布）基础上增加视觉能力的**实验版**，共享同一模型结构与参数规模；纯文本能力与 V4-Flash 一致。
- **视觉**：支持图文混合输入、截图 OCR、图表分析；**视觉能力需手动声明启用**（不会自动生效）。
- **协议**：OpenAI 兼容格式（同时支持 Anthropic 格式）；流式输出 `stream=true` 官方支持。
- **Agent/工具**：官方更新日志称其在「需要视觉理解的 Agent Benchmark」上较 V4-Flash 大幅提升，多模态 Agent 能力接近 Opus-4.8（官方表述）；DeepSeek V3.2 起官方即支持「思考模式下多轮工具调用」。
- 来源：[DeepSeek 官方更新日志](https://api-docs.deepseek.com/zh-cn/updates)、[官方发布公告 2026-08-21](https://api-docs.deepseek.com/zh-cn/news/news260821/)、[七牛云转述](https://news.qiniu.com/archives/1787305976028)、[IT之家（媒体）](https://www.ithome.com/0/992/755.htm)。

### 2.3 Qwen3.8-Flash（阿里，2026-08-26 发布并开源）

- **规格**：多模态 MoE，被称为 Qwen4 架构早期预览版；千亿级总参、约 6B 激活；原生百万级上下文。
- **价格**：输入约 0.8~1 元/百万 tokens、输出约 2.7~3 元/百万 tokens（媒体汇总，社区信息）。
- **工具调用**：开启思考模式后，工具调用前输出 `reasoning_content`；**多轮工具调用需将 reasoning_content 一并回传**，否则可能影响效果（千问平台开发者文档）。
- **基准**：媒体称多模态/编程/智能体基准超越 Claude Opus 4.6 与 DeepSeek-V4-Flash（社区信息，未见我方核实的一手 benchmark）。
- 来源：[千问AI平台模型页](https://www.qianwenai.com/models/qwen3.8-flash)、[阿里云百炼](https://www.aliyun.com/product/bailian)。

### 2.4 GPT-5.6-Luna（OpenAI，2026-06-26 预览 / 2026-07-08 公开）

- **定位**：GPT-5.6 家族（Sol/Terra/Luna 三档）中的 **nano 级**，面向高吞吐、低成本、低延迟场景，跳过重推理步骤。
- **价格**：2026-07-30 官方宣布 Luna 降价 80%。
- **视觉+工具**：OpenRouter 模型页明确「vision requests can now use JSON mode and function calling」；Roboflow 证实三档模型视觉能力可用（第三方平台信息）。
- 来源：[OpenAI API Docs GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)、[GPT-5.6 官方公告](https://openai.com/index/gpt-5-6/)、[OpenRouter](https://openrouter.ai/openai/gpt-5.6-luna)、[CNBC 报道](https://www.cnbc.com/2026/07/08/openai-expanding-gpt-5point6-ai-model-release-ending-government-limits.html)。

## 3. 协议能力现状（OpenAI 兼容口径）

### 3.1 流式 + 工具调用共存

- GLM-5.3-Flash：官方能力表同时列出「流式输出」与「Function Calling（含流式工具调用）」。
- DeepSeek：官方文档标准用法即 `stream=true` + tools；思考模式下「思考+工具调用」交替进行（V3.2 起）。
- Gemini 3 系：function calling 与流式为常规组合；官方文档明确 Structured Outputs 可与内置工具组合使用（Gemini 3 起）。
- 近三个月检索中**未发现**任何主流厂商存在「流式与 tools 互斥」的现行问题（历史上的 Gemini 兼容层问题仅见于旧资料）。

### 3.2 结构化输出（response_format）

| 厂商 | 文本输出 strict json_schema | 工具参数 strict |
|---|---|---|
| OpenAI | ✅（structured outputs，约束解码） | ✅（strict functions） |
| Qwen（百炼/千问平台） | ✅ 完整支持 `json_schema` + `strict: true` | ✅ |
| GLM（智谱） | ✅ 官方「结构化输出」文档支持严格 JSON Schema | ✅（Agent 场景优化） |
| DeepSeek | ⚠️ 仅 `json_object`（需 prompt 提示），无 strict json_schema | ✅ tool calls 支持 strict 模式 |

- 聚合平台提醒（无问芯穹 Infini-AI 文档）：**`function.strict` 与 `response_format.json_schema.strict` 是两个独立能力**，模型支持其一不代表支持另一个；既要调工具又要结构化结果时建议分两步。
- OpenAI 官方 Structured Outputs 与 Parallel Function Calling 存在已知互操作问题（社区反馈：并行调用时参数可能不匹配 schema）。
- 来源：[OpenAI Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)、[Qwen 结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)、[GLM 结构化输出](https://docs.bigmodel.cn/cn/guide/capabilities/struct-output)、[DeepSeek JSON Output](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/zh-cn/guides/tool_calls)、[Infini-AI 提醒](https://docs.infini-ai.com/gen-studio/api/text-generation/tutorial-function-calling.html)、[OpenAI 社区反馈（社区）](https://community.openai.com/t/partially-structured-output-free-text-output-but-force-correct-tool-call-json/955147)。

### 3.3 并行工具调用

- DeepSeek：Function Calling 支持并行（官方称最多 128 个 function）；Responses API 兼容端点上 `parallel_tool_calls` 参数被**忽略**（并行始终开启）。
- OpenAI/Qwen/GLM：均支持并行 tool calls；网易云信等托管方提供 `parallel_tool_calls` 开关。
- 来源：[DeepSeek 并行 Function 调用公告](https://api-docs.deepseek.com/zh-cn/news/news0725)、[DeepSeek Responses API](https://api-docs.deepseek.com/zh-cn/api/create-response/)。

### 3.4 思考型模型的 `reasoning_content` 处理（接入候选模型的前置知识）

- **Qwen**：`enable_thinking=True` 时工具调用前返回 `reasoning_content`；多轮工具调用需一并回传。
- **GLM**：DashScope 文档列明 `reasoning_content` 可作为上下文回传（glm-5.2/5.1/5/4.7 支持）；自适应思考模式下不保证每次都返回该字段；**思考模式不支持强制指定工具（tool_choice 强制）**。
- **DeepSeek**：V3.2 起思考模式下多轮工具调用为官方能力。
- **腾讯混元**：要求每一轮请求回填历史 reasoning_content（交错思考模式）——佐证「是否回传/如何回传」各厂商存在差异。
- **共识**（网易云信汇总）：Qwen/Kimi/DeepSeek/GLM 等推理模型的历史推理字段**只在目标厂商要求时原样回传，不拼入 content**。
- **自部署框架**：vLLM / LMDeploy 均服务端自动分离 `reasoning_content` 与正文。
- 来源：[阿里云深度思考模型用法](https://help.aliyun.com/zh/model-studio/deep-thinking)、[千问平台函数调用](https://platform.qianwenai.com/docs/developer-guides/tool-calling/function-calling)、[DashScope API 参考](https://www.alibabacloud.com/help/zh/model-studio/qwen-api-via-dashscope)、[GLM thinking 文档](https://docs.infini-ai.com/gen-studio/api/text-generation/tutorial-reasoning/glm.html)、[腾讯云文档](https://intl.cloud.tencent.com/zh/document/product/1300/80637)、[vLLM 文档](https://vllm.hyper.ai/docs/features/reasoning_outputs/)。

### 3.5 Responses API

- DeepSeek 已提供 OpenAI **Responses API 兼容端点**（2026 年现行）；OpenAI 自身主推 Responses API 作为 Chat Completions 的演进方向。项目当前仅用 Chat Completions（`chat.completions.create`）。

## 4. 与本项目现状的对应事实（仅列差距，不给方案）

1. 项目全部 JSON 输出场景（supervisor 路由）靠 prompt+正则，而候选模型多数支持 strict 结构化输出（DeepSeek 例外，仅 json_object）。
2. 项目未处理 `reasoning_content`；候选模型默认思考模式（GLM-5.3-Flash 恒开思考），思考内容与多轮回传规则是接入即会遇到的问题。
3. 项目同批 tool_calls 串行执行；DeepSeek 等默认并行返回多个 tool calls。
4. 项目对「流式+tools」「图+tools」做互斥回退；现行模型无此限制。
5. 项目未用 tool_choice；注意思考模式（Qwen/GLM）下**不支持强制工具调用**——这是现行生态的真实约束而非项目缺陷。
6. 项目所用 openai SDK 2.26 已支持 Responses API/strict 等新特性，版本层面无障碍。
