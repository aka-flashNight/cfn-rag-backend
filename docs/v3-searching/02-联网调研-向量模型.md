## 3. 推理加速与打包

### 3.1 ONNX Runtime / OpenVINO

- sentence-transformers v3.2.0（2024-10）起内置 **ONNX / OpenVINO 后端**，官方基准（i7-13700K）为**相对 PyTorch fp32 的 2~3x CPU 提速**；v4.1（2025-04）扩展到 reranker。sbert 提供 `backend="openvino"` 一行切换。【官方】来源：[sbert efficiency 文档](https://sbert.net/docs/sentence_transformer/usage/efficiency.html)
- 社区共识：ONNX Runtime 在 **CPU、小 batch** 场景比 PyTorch 快 2~10x；batch 增大差距缩小。【社区】来源：[Medium 实测](https://medium.com/@manevaish17/make-your-models-fly-onnx-runtime-latency-gains-for-pytorch-with-9e26d645889e) 等

### 3.2 int8 量化

- **Vespa 严格基准（<500M 参数、有 ONNX 权重的模型）：CPU int8 提速 2.7~3.4x，质量保留 94~98%；GPU 上 int8 反而比 fp32 慢 4~5x**。【社区实测】来源：[Vespa: Embedding tradeoffs quantified](https://blog.vespa.ai/embedding-tradeoffs-quantified/)
- 体积：int8 ≈ fp32 的 1/4（90MB fp32 → ~25MB int8）。【社区实测】同上
- 动态量化是 ONNX 模型的首选起点。【社区共识】来源：[HF Optimum 文档](https://huggingface.co/docs/optimum/en/concept_guides/quantization)

### 3.3 相关库状态（2026）

- **sentence-transformers**：2025 年中 v5.0（SparseEncoder 等），2026 年初 v5.6.x，随后 **v6.0（MultiVectorEncoder）**；要求 Python 3.10+、torch 2.2+、transformers v5+。【官方】来源：[releases](https://github.com/UKPLab/sentence-transformers/releases)
- **fastembed**：默认 `BAAI/bge-small-en-v1.5`；**支持 bge-small-zh-v1.5（ONNX、90MB，其列表中唯一中文专用模型）**；不支持 Qwen3-Embedding / gte-multilingual；社区 issue #292 报告部分同步调用场景 fastembed 慢于 sentence-transformers。【官方+社区】来源：[支持表](https://qdrant.github.io/fastembed/examples/Supported_Models/)、[issue #554](https://github.com/qdrant/fastembed/issues/554)、[issue #292](https://github.com/qdrant/fastembed/issues/292)
- **infinity-emb**：最后一次 PyPI 发布 2025-08-22，2026 年无新版本，活跃度存疑；TEI 面向 Docker/Linux 服务器而非 Windows 单机打包。【官方】来源：[PyPI](https://pypi.org/project/infinity-emb/)
- 自带 ONNX 权重的现成中文小模型：**fastembed 的 bge-small-zh-v1.5 是唯一开箱即用选项**；其他模型需自行 `optimum-cli export onnx` 后分发 .onnx。【社区共识】

### 3.4 PyInstaller 打包体积对比

| 组件 | wheel 体积（Windows x64） | 安装后占用 |
|---|---|---|
| torch 2.14.0 CPU 版（2026-09-02） | 124.1 MB | ~430MB（社区实测） |
| onnxruntime 1.29.0（2026-08-17） | 14.0 MB | 约 40~60MB（含 DLL） |

【官方（wheel 体积）】来源：[PyPI onnxruntime](https://pypi.org/project/onnxruntime/#files)、[PyPI torch](https://pypi.org/project/torch/#files)；【社区（安装后）】来源：[HN 讨论](https://news.ycombinator.com/item?id=43096492)

- 社区案例：ONNX + onnxruntime 打包纯 CPU exe 约 **83MB**（对比 torch 打包普遍 GB 级）；标准做法是**离线完成 ONNX 转换、exe 只带 .onnx 文件**。【社区实测/共识】来源：[CSDN 案例](https://blog.csdn.net/LaLaLaLaXFF/article/details/122299340)、[PyInstaller issue #8551](https://github.com/pyinstaller/pyinstaller/issues/8551)
- 本项目口径推算（非搜索结论）：357MB exe 中 torch 栈约占 150~250MB、模型 92MB；换 onnxruntime + int8 模型（~25MB）有约一个数量级的下降空间。

## 4. 检索侧事实

### 4.1 轻量 reranker

- bge-reranker 家族：base（~278M，2023）→ **v2-m3（~568M，官方定位「轻量、多语、快推理」，2024）** → v2.5-gemma2-lightweight（9B 基座+token 压缩，2024-07）。【官方】来源：[bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3)
- CPU 上 reranker 每对 query-doc 一次前向，延迟是主要代价；sbert v4.1+ 的 CrossEncoder 支持 ONNX/OpenVINO 后端（2~3x）。【社区+官方】来源：[Speed Showdown](https://medium.com/@xiweizhou/speed-showdown-reranker-1f7987400077)

### 4.2 BM25 + 向量 hybrid（2026 常规做法）

- 标准链路：BM25（中文需分词，如 jieba）与 dense 并行召回 → **RRF（k=60）** 或加权融合 → 可选 cross-encoder 重排。【社区共识】来源：[Hybrid Search Reference 2026](https://www.digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026)、[supermemory 2026-04](https://supermemory.ai/blog/hybrid-search-guide/)
- Vespa 基准：**每个模型 hybrid 均优于纯语义检索，平均 +3~5pp nDCG**。【社区实测】来源：[Vespa](https://blog.vespa.ai/embedding-tradeoffs-quantified/)
- 小语料坑：**极小语料（~80 篇）上默认 RRF k=60 的 hybrid 可能劣于纯 dense**；另一 2026 基准（arXiv 2604.01733）结论 hybrid 整体更优、增益在小 k 最大，部分场景 BM25 反超 dense。【社区实测】来源：[gopenai 博客](https://blog.gopenai.com/hybrid-search-in-rag-dense-sparse-bm25-splade-reciprocal-rank-fusion-and-when-to-use-which-fafe4fd6156e)、[arXiv 2604.01733](https://arxiv.org/html/2604.01733v1)

## 5. 纯 CPU embedding 吞吐量参考

- **all-MiniLM-L6-v2（22M，与 bge-small 同级）PyTorch CPU：约 200~1300 句/秒**（设备与句长而异）；约 8ms/passage。【社区实测】来源：[fastembed #292（~1300 条/s）](https://github.com/qdrant/fastembed/issues/292)、[Reddit](https://www.reddit.com/r/LocalLLaMA/comments/1s9pnla/)（注：HF 流传的「14,200 句/秒」是 GPU 数据）
- **int8+ONNX（Graviton3）**：E5-small-v2 单 query 编码 **2.5ms**（8 词）。【社区实测】来源：[Vespa](https://blog.vespa.ai/embedding-tradeoffs-quantified/)
- **StaticEmbedding（非 BERT 架构）**：CPU 数千句/秒（sbert 官方称部分场景相对 BERT 类 ~500x）。【官方口径+社区】来源：[sbert efficiency](https://sbert.net/docs/sentence_transformer/usage/efficiency.html)、[HN](https://news.ycombinator.com/item?id=46081800)
- **换算到本项目（推算，非实测）**：几千~几万条游戏数据、bge-small 级模型 CPU 百级句/秒 → 首次全量索引为「数十秒到数分钟」量级；ONNX/OpenVINO + int8 常见 2~3x 提速。未检索到 bge-small-zh-v1.5 的公开逐条 CPU 吞吐实测（英文社区基准不含它），为同级模型推算。
- 参数量与 CPU 速度量级关系（推算）：Qwen3-Embedding-0.6B（595M）参数为 bge-small（24M）的 ~25 倍，CPU 吞吐约低 1~1.5 个数量级；Gorse 确认 0.6B 是 Qwen3 系列唯一适合端侧的档位。【社区评测】

## 6. 与本项目现状的对应事实（仅列差距）

1. 当前模型本体只有 92MB / 24M 参数——「模型太大」并非体积与首次索引慢的主因；**torch/transformers 推理栈（exe 357MB 的主因）与逐条 CPU 推理方式**才是重量来源（对照 §0.1、§3.4）。
2. 项目内的维度记录（384 维）与模型实际（512 维）不符（本地 config 证实；见问题清单 C7）。
3. 当前嵌入链路经 LlamaIndex HuggingFaceEmbedding 每次调用重算；对照 §5 吞吐数据与 §3.1 的 ONNX/OpenVINO 提速事实。
4. 项目已有 BM25+RRF 实现（bm25_retrieval.py）但生产未启用；2026 年社区共识的 hybrid 做法与该实现形态一致（RRF k=60），并有「极小语料 RRF 可能劣于纯 dense」的注意事项（本项目语料为几千~几万条，不在极端小语料区间）。
5. 项目打包单 exe：社区标准替代路径（离线 ONNX + onnxruntime，约 14MB wheel / 40-60MB 安装后）与当前 torch 栈（124MB wheel / ~430MB 安装后）的量化对照见 §3.4。

## 7. 补充调研（2026-09-05 追问）：「几 MB 级」文本向量模型与人脸向量模型的体积差距来源

### 7.1 事实：几 MB 级文本向量模型确实存在，但集中在「静态向量（static embedding）」路线

- **静态向量模型**（非 Transformer：词向量查表 + 轻量投影/MRL 截断）：
  - HF 官方博客（2024-11）：static 模型在 CPU 上比 SOTA Transformer embedding **快 100~400 倍**，模型本体为查表结构、天然适合 int8。【官方】来源：[Static Embeddings with sentence-transformers](https://huggingface.co/blog/static-embeddings)
  - 社区实例：**7.2MB embedding 模型，比 MiniLM 快 80 倍、指标差 5 分以内**。【社区实测】来源：[Reddit r/LocalLLaMA](https://www.reddit.com/r/LocalLLaMA/comments/1s9pnla/i_made_a_72mb_embedding_model_thats_80x_faster/)
  - 官方现成模型：`static-retrieval-mrl-en-v1`（**仅英文**，检索档）；`static-similarity-mrl-multilingual-v1`（50+ 语言，**但只有相似度档、无检索档**，中文检索质量无 C-MTEB 收录）。【官方，中文检索档缺失为关键事实】
- **Transformer 阵营的最小档**：all-MiniLM-L6-v2（22M 参数 ≈ 90MB fp32 / ~23MB int8）、gte-tiny（~17M，~46MB）、m3e-small / bge-small-zh（24M，~95MB fp32）。【社区+官方】来源：[Xinference bge-small-zh](https://inference.readthedocs.io/zh-cn/v1.15.0/models/builtin/embedding/bge-small-zh.html)、[HN 讨论](https://news.ycombinator.com/item?id=46081800)
- **中文现状**：主流注册表（fastembed 等）中最小中文句向量模型即 24M/90MB 档；**未发现「几 MB + 中文检索质量可用」的现成开源模型**。纯静态中文词向量存在（腾讯 AI Lab 800 万词 200 维），但全表数百 MB 且按词查表、非句向量。【社区确认】
- 生态信号：浏览器端推理引擎 TinyLM（ONNX/WASM 跑 NomicEmbed 等）说明端侧小模型路线活跃，但非中文检索档。来源：[wizenheimer/tinylm](https://github.com/wizenheimer/tinylm)

### 7.2 事实：人脸向量模型为什么能几 MB（对照解释）

- MobileFaceNet（2018，ArcFace + 精炼 MS1M 训练）：**~1.0~1.1M 参数、4.0MB（fp32）、int8 后约 1MB**，输入固定 112×112 对齐人脸，输出 512 维，LFW 99.55%。【官方/论文】来源：[MobileFaceNets 论文](https://arxiv.org/pdf/1804.07573)、[轻量改进版 arXiv 2311.15326](https://arxiv.org/html/2311.15326v1)
- 可小的结构性原因（论文与社区口径汇总）：
  1. **任务封闭**：输入分布固定（检测+对齐后的 112×112 人脸裁剪），目标单一（身份判别）；
  2. **架构匹配**：MobileNet 式 depthwise separable 卷积 + GDWC 头，无 Transformer、无词表；
  3. **知识在库里不在模型里**：识别靠底库比对，模型只需学好「人脸表征」，世界知识不需要压进权重；文本检索的语义知识必须进权重；
  4. **监督信号直接**：数百万带身份标签的图像直接优化目标指标；文本 embedding 靠弱监督对比学习，容量需求更高；
  5. **分发即 int8**：移动端部署默认量化，发布的 artifact 就是 ~1MB；文本模型社区惯例仍以 fp32 safetensors 分发（同模型 int8 可缩为 1/4）。

### 7.3 本机实测（2026-09-05，开发机 14 线程 CPU，torch 2.10.0+cpu，项目同款 bge-small-zh-v1.5 与真实 4426 条文档）

【本机实测，非检索结论】

- **实际索引规模**：4426 条节点（task 1547 / game_item 1618 / intelligence 382 / dialogue 352 / lore 285 / stage 143 / loading 99），平均 101 字符（中位 68、P90 223、最大 2416），总 45.1 万字符；索引目录 58MB（其中 default__vector_store.json 50MB —— 4426×512 fp32 向量按 **JSON 文本** 存储，二进制本应 9.1MB，文本化膨胀 ~5.5 倍）。
- **吞吐与延迟**（fp32 vs torch 动态 int8 量化，真实文档采样）：

| 指标 | fp32（现状同款） | torch 动态 int8 | 变化 |
|---|---|---|---|
| 批量吞吐（batch=10，项目默认） | 102 条/s | 141 条/s | **1.38x** |
| 批量吞吐（batch=64） | 87 条/s | 130 条/s | 1.49x |
| 单条查询编码延迟（中位） | 62.4ms | 21.5ms | **2.90x** |
| 单条查询编码延迟（P90） | 91.2ms | 29.2ms | 3.1x |
| 模型文件体积 | 91.9MB | 57.3MB（state_dict 序列化） | 1.6x |

- **关键解释**：torch 动态量化只量化 Linear 层（12.6M 参数→int8），**词嵌入表（21128×512=10.8M 参数、43MB fp32）保持 fp32**，故体积只到 57MB 而非 1/4；全量静态 int8（ONNX 路线）才约 25MB。批量加速 1.4~1.5x 低于 Vespa ONNX 基准的 2.7~3.4x（后者为 ONNX Runtime int8 内核），单条延迟收益（~3x）与之接近。
- **全量重建耗时实测推算**（4426 条，不含文档解析/模型加载）：
  - fp32（现状）：批量 10 ≈ **43 秒**（README 自述 10~30 秒偏乐观，或数据量已增长/机器不同）
  - torch 动态 int8：≈ **31~34 秒**
  - ONNX Runtime int8（研究数据 2~3x 推算）：≈ **15~22 秒**
- **对本项目检索链路的实际意义**：`_retrieve_context` 单轮 12~16 次 query 编码（问题清单 C1），fp32 下仅 query 编码即 0.75~1.0 秒/轮，int8 后降至 0.26~0.34 秒/轮。
- **注意**：模型权重 int8 与「向量存储精度 int8」是两回事；前者不动 50MB 的 JSON 向量存储（那是序列化方式问题，二进制 fp32 即 9.1MB、int8 存储 2.3MB）。
- 未实测项：ONNX Runtime 路线本机未装 onnxruntime/optimum，未做真实转换基准；上表 ONNX 行为研究数据推算，已标注。
